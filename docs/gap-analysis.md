## 총평

세 문서는 **기획·정책·안전 설계 측면에서 이미 밀도가 높습니다.** 특히 가드레일 설계(초안 5장), 인사담당자 콘텐츠 운영 관점(6.3), 개인화 경계 원칙(4.5)은 해커톤 수준을 넘어섭니다. 문제 정의와 제외 범위도 명확합니다.

문제는 **"무엇을 만들 것인가"는 잘 적혀 있는데 "어떻게 만들 것인가"가 통째로 비어 있다**는 점입니다.

## 특히 중요한 5건 — 먼저 읽어주세요

나머지는 표로 훑어도 되지만, 이 다섯은 판단의 성격이 다릅니다.

### 1. 배포 환경과 문서가 주장하는 환경이 서로 다르다 (A1)

세 문서 전체가 **"사내 문서·질문·임베딩·추론이 외부로 나가지 않는다"** 를 핵심 가치로 걸고 있습니다. 초안 7행, 구축 가이드 5행이 그 문장으로 시작합니다. 그런데 실제 프로토타입은 온프렘 환경이 아닌 곳에 배포됩니다.

이 사실이 문서 어디에도 없습니다. 심사위원이 배포된 URL을 보는 순간 **가장 먼저 나올 질문**이고, 문서에 대비가 없으면 "원칙과 구현이 따로 논다"로 읽힙니다.

이건 숨길 게 아니라 **의도된 설계 결정으로 전환**해야 하는 사안입니다.

> On-premise는 **설계 문서로 증명**하고, RAG 동작·가드레일·인용은 **실행되는 프로토타입으로 증명**한다.
> 프로토타입은 합성 문서만 쓰므로 배포 환경에서도 실제 사내 데이터가 외부로 나가지 않는다.
> 온프렘 전환은 코드 수정이 아니라 **모델 백엔드 설정 교체**로 이루어지도록 설계한다.

이렇게 선언하면 약점이 아니라 오히려 "범위를 정확히 구분할 줄 안다"는 강점이 됩니다. 조치는 4문서 앞부분에 **대조표 한 개**를 넣고, 챗봇 화면에 현재 모드 배지를 다는 정도로 끝납니다. 비용 대비 효과가 가장 큰 항목입니다.

### 2. "근거 부족" 판정 임계값이 숫자로 없다 (B3)

초안 5.1은 근거 없는 답변의 위험 기준을 *"검색 점수 낮음, 인용 문서 없음, 문서 간 충돌"* 로 적었습니다. 이용 가이드 4장, 구축 가이드 6장도 같은 취지입니다.

그런데 **"낮음"이 몇 점인지가 없습니다.** 이 값 하나가 이 챗봇의 성격을 결정합니다. 너무 높으면 정상 질문까지 전부 "인사팀에 문의하세요"로 빠져서 시연이 무너지고, 너무 낮으면 근거가 빈약한데도 답을 지어냅니다. 그리고 검증 원칙(8.3)이 *"안전하게 모른다고 말하는지를 필수 통과 기준으로 둔다"* 고 못박아 놨기 때문에, 이 숫자는 **KPI 통과 여부를 직접 결정**합니다.

숫자와 **그 숫자를 정한 근거**(골든셋에서 어떻게 튜닝했는지)까지 문서에 남겨야 합니다.

### 3. 개인화 판정 규칙이 자연어뿐이라 경계 케이스에서 바로 막힌다 (B7)

초안 2.2가 정한 건강검진 가정은 두 줄입니다. *"신규 입사자는 입사 다음 해 대상"*, *"계속 근로자는 2년에 1회"*.

이걸 코드로 옮기는 순간 답이 없는 질문이 쏟아집니다.

- 2026년 12월 20일 입사자는 "다음 해"인 2027년 대상인가? 열흘 근무하고?
- "2년에 1회"의 기준 연도는 입사 연도 기준인가, 짝수/홀수 연도인가? 사람마다 다른가 전사 공통인가?
- **이직 경력 입사자는 "신규"인가 "계속"인가?** 데모 사용자 `345678`이 정확히 이 경우입니다
- 연말정산에서 입사 당해 연도인 사람은 어느 분기로 가는가?

지금 상태로 구현하면 이 판단들을 제가 코딩하면서 임의로 정하게 되고, 문서에는 안 남습니다. 그러면 시연 중 "그 사람은 왜 대상이 아닌가요?"라는 질문에 답할 근거가 없습니다. **결정 테이블 하나**로 해결됩니다.

### 4. KPI를 걸어놓고 측정할 데이터가 없다 (C1)

초안 8.1은 Recall@K, 근거 정확성, 인용 충실도를 지표로 제시합니다. 그런데 그걸 측정할 질문셋은 10장 "후속 확정이 필요한 항목"으로 미뤄져 있습니다.

**현재 상태로는 KPI 수치를 하나도 낼 수 없습니다.** 발표에서 "정확도가 높습니다"라고 말만 하게 됩니다.

25~30문항짜리 골든셋(질문 / 정답 문서ID / 기대 동작)이면 충분하고, 이건 만드는 즉시 두 가지로 동시에 쓰입니다. **정량 KPI 근거**이자 **자동 회귀 테스트**입니다. 초안 7장 단계6의 안전 시나리오 8종도 여기에 흡수하면 기대 출력이 정의되어 자동 판정이 가능해집니다. 투입 대비 회수가 가장 큰 항목입니다.

### 5. 온프렘을 선택한 규제적 근거가 비어 있다 (D9)

문서 전체가 온프렘의 이유를 "안전하니까"로 설명합니다. 이건 심사에서 "그냥 클라우드 RAG 쓰면 안 되나요?"에 밀립니다.

실제로는 법적 근거를 댈 수 있는 영역입니다.

- **개인정보보호법** — 최소수집·목적제한 원칙, 처리위탁 시 국외이전 고지. 초안 4.5의 "개인정보를 벡터DB에 넣지 않는다"는 설계가 이 원칙의 구현입니다
- **산업안전보건법 일반건강진단** — 사무직 2년 1회, 그 외 1년 1회로 알려져 있습니다. 초안 2.2의 *"2년에 1회 가정"* 은 사실 임의 가정이 아니라 **법정 주기와 일치**합니다. 근거를 달면 "가정"이 "현실 반영"이 됩니다
- **소득세법·연말정산** — 원천징수영수증 등 이직자 증빙 요구의 근거

> ⚠️ 저는 법률 자문을 드릴 수 있는 입장이 아니고, 위 조항은 개정될 수 있습니다. 문서에는 **"조문 원문 및 담당자 확인 필요"** 표기와 함께 넣고, 확정은 검토를 거치는 걸 전제로 합니다.

## D. 구축 가이드의 설계 깊이

**과제의 핵심 절반**(*"On-premise 환경 구축 방안은 문서로 설계"*)인데, 현재 구축 가이드는 개념·원칙 수준에 머물러 있습니다. 체크리스트와 원칙은 좋지만, **이 문서만 보고 실제로 구축할 수는 없습니다.** 온프렘을 코드로 증명하지 않기로 한 이상, 이 문서의 깊이가 그 절반의 점수를 결정합니다.

| # | 공백 | 제안 조치 | 등급 | 판단 |
|---|---|---|---|---|
| D1 | 서버 사양·자원 산정 없음 | GPU VRAM(모델 크기별), CPU/RAM/디스크, 동시 사용자 수 대비 처리량 산정표 | 🔴 | |
| D2 | 컨테이너 구성표 없음 | 이미지·포트·볼륨·네트워크 세그먼트 표 + docker-compose 수준 명세. 구축 가이드 1장 다이어그램을 실행 가능한 형태로 | 🔴 | |
| D3 | 오프라인 반입 절차가 개념만 | 모델 파일 해시 검증, 내부 레지스트리 미러링, 반입 승인 기록 양식 | 🟠 | |
| D4 | 모니터링·관측 스택 구체 없음 | 수집 지표 항목 목록 + 도구 후보. 초안 8.1의 P50/P95를 어디서 어떻게 재는지 | 🟠 | |
| D5 | 백업·DR의 RTO/RPO 수치 없음 | 목표 복구 시간·복구 시점 수치화. 벡터 인덱스는 재생성 가능하므로 원문 저장소와 백업 등급을 분리 | 🟡 | |
| D6 | **로그 보존 기간이 숫자로 없다** ("최소 수집"만) | 로그 유형별 보존 기간 표 (질의 로그 / 감사 로그 / 오류 로그). 개인정보 관점에서 수치 없이는 무의미하다 | 🔴 | |
| D7 | 단계별 구축 절차·체크리스트 없음 | Day 1~N 구축 순서. **문서만 보고 재현 가능한가**가 이 문서의 합격 기준이다 | 🟠 | |
| D8 | SaaS 대비 TCO 비교 없음 | 초기 구축비 + 운영비 vs 외부 API 종량제 비교. "안전하니까"를 넘어선 근거 | 🟠 | |
| D9 | **법·규정 매핑 없음** | 위 상세 참조. 개인정보보호법 / 산업안전보건법 / 소득세법. **조문 확인 필요 표기 필수** | 🟡 | |

## E. 운영·UX 공백
