## 0. 세 줄 요약

1. 문서를 고치면 **검토·승인을 거쳐** 자동으로 챗봇에 반영됩니다.
2. **Git 명령어를 몰라도 됩니다.** 소스트리(SourceTree)라는 프로그램에서 마우스로 합니다.
3. 잘못 고치면 **검증에서 걸려 배포되지 않습니다.** 실수해도 서비스는 안전합니다.

---

## 1. 왜 공유 폴더가 아니라 Git인가

파일을 폴더에서 바로 고치면 세 가지가 안 됩니다.

| | 공유 폴더 | Git |
|---|---|---|
| 누가 언제 무엇을 바꿨는지 | 남지 않음 | **자동으로 남음** |
| 검토 없이 발행되는 것 | 막을 수 없음 | **승인 없이는 반영 안 됨** |
| 잘못 고쳤을 때 | 되돌리기 어려움 | **한 번에 되돌림** |

특히 **권한 설정을 잘못 바꾸면 볼 수 없어야 할 사람이 문서를 보게 됩니다.** 그런 변경이
아무 흔적 없이 일어나지 않도록 하는 것이 이 절차의 목적입니다.

---

## 2. 처음 한 번만 하는 준비

### 2.1 소스트리 설치

사내 소프트웨어 배포 포털에서 **SourceTree**를 설치합니다. 외부에서 내려받지 않습니다.

### 2.2 저장소 연결 (클론)

1. 소스트리를 열고 **`Clone`** 을 누릅니다.
2. **소스 경로/URL**에 사내 Git 주소를 붙여 넣습니다 (IT팀이 안내한 주소).
3. **목적지 경로**는 기본값을 그대로 둡니다. 어디에 저장되는지만 기억해 두세요.
4. **`Clone`** 을 누르면 문서 폴더가 내 PC에 내려받아집니다.

내려받은 폴더 안 `prototype/data/knowledge/` 에 문서 파일들이 있습니다. 파일 하나가 문서 하나입니다.

---

## 3. 문서 고치기 — 소스트리에서 5단계

> **원칙: `main`에서 바로 고치지 않습니다.** 항상 새 브랜치를 만들어 고칩니다.
> 소스트리가 어느 브랜치인지 왼쪽 위에 항상 보여줍니다.

### ① 최신 상태로 맞추기

작업 시작 전 **`Pull`** 을 누릅니다. 다른 사람이 바꾼 내용을 먼저 받아옵니다.
이걸 건너뛰면 나중에 충돌이 납니다.

### ② 새 브랜치 만들기

1. 상단 **`Branch`** 를 누릅니다.
2. 이름을 알아보기 쉽게 적습니다 — 예: `hr/건강검진-대상연도-수정`
3. **`Create Branch`**

### ③ 문서 고치기

내려받은 폴더에서 해당 `.md` 파일을 메모장이나 편집기로 엽니다. 필요한 부분만 고치고 저장합니다.

**문서 맨 위 `---` 사이 영역을 조심하세요.** 여기가 챗봇의 동작을 정하는 설정입니다.

```yaml
---
title: 건강검진 운영 안내        ← 문서 제목
version: "0.1"                 ← 내용을 고쳤으면 0.2로 올립니다
acl_groups: [all_employees]    ← ★ 누가 볼 수 있는지. 함부로 바꾸지 마세요
valid_until: 2027-02-09        ← 이 날짜가 지나면 챗봇이 답하지 않습니다
---
```

### ④ 커밋 (변경 사항 기록하기)

1. 소스트리 왼쪽 **`File Status`** 를 누르면 고친 파일이 보입니다.
2. 파일을 선택하고 **`Stage Selected`** 를 누릅니다.
3. 아래 입력창에 **무엇을 왜 바꿨는지** 한 줄로 적습니다.
   - 좋은 예: `건강검진 대상 연도 표 오류 수정 (2029→2028)`
   - 나쁜 예: `수정`, `ㅇ`, `업데이트`
   - 이 문장이 그대로 **감사 기록**에 남습니다.
4. **`Commit`**

### ⑤ 푸시하고 검토 요청

1. 상단 **`Push`** 를 누릅니다.
2. 사내 Git 웹 화면에 들어가 **`Merge Request`(또는 `Pull Request`)** 를 만듭니다.
3. 검토자를 지정합니다. **본인은 본인 요청을 승인할 수 없습니다.**
4. 승인되고 병합되면 **자동으로 챗봇에 반영**됩니다.

---

## 4. 검증에서 걸렸을 때

병합 요청을 올리면 자동 검사가 돌아갑니다. 실패하면 아래 메시지가 뜹니다. **당황하지 말고
해당 항목만 고쳐서 다시 커밋·푸시하면 됩니다.**

| 메시지 | 뜻 | 대처 |
|---|---|---|
| `필수 필드 누락: [...]` | 문서 맨 위 설정에 빠진 항목이 있음 | 목록에 나온 항목을 다른 문서에서 복사해 채웁니다 |
| `doc_id 중복` | 다른 문서와 같은 번호를 씀 | 번호를 새로 부여합니다 |
| `valid_until이 published_at보다 늦어야 합니다` | 유효기간이 발행일보다 빠름 | 날짜를 확인합니다 |
| `demo_assumption=true인데 데모 고지가 없습니다` | 가정 문서인데 안내 문구가 빠짐 | 본문 맨 앞에 데모 고지 문단을 넣습니다 |
| `doc_type=규정이면 authority_level을 선언해야 합니다` | 규정 문서인데 위계를 안 적음 | 인사팀에 확인해 `취업규칙`·`사규`·`부서지침` 중 하나를 적습니다 |
| `골든셋 회귀` | **이 문서 수정 때문에 다른 질문의 답이 틀어졌음** | 아래 5장을 읽어 주세요 |
| `조문은 있는데 항 기호(①②③)가 없습니다` | 변환 과정에서 항 번호가 사라짐 | 원본과 대조해 `①②③`을 복원합니다 |

### 골든셋 회귀가 났다면

문서 하나를 고쳤는데 **관계없어 보이는 다른 질문의 답이 바뀐 것**입니다. 흔한 원인은 둘입니다.

- **절 제목을 바꿨다** — 챗봇은 절 제목을 가장 중요하게 봅니다. 제목이 바뀌면 검색 결과가 바뀝니다.
- **문장을 지웠다** — 그 문장이 다른 질문의 답이었을 수 있습니다.

되돌리거나, 어느 질문이 깨졌는지 확인해 문서를 보강합니다. 판단이 어려우면 **IT팀에 요청**하세요.

## 5. 절대 하면 안 되는 것

| 하지 말 것 | 이유 |
|---|---|
| `main` 브랜치에서 바로 고치기 | 검토 없이 배포됩니다 |
| 서버 폴더의 파일을 직접 고치기 | 다음 배포 때 덮어써지고, 기록도 남지 않습니다 |
| `acl_groups`·`sensitivity`를 임의로 바꾸기 | **볼 수 없어야 할 사람이 보게 됩니다.** 인사팀·보안 승인 필요 |
| `authority_level`·`statutory` 임의 변경 | 규정 우선순위와 법정 기준 안내가 뒤바뀝니다. 인사팀 승인 필요 |
| 실명·실제 연락처·주민등록번호를 문서에 넣기 | 챗봇 답변에 그대로 노출됩니다 |
| 커밋 메시지를 대충 쓰기 | 감사 기록이 무의미해집니다 |

> **위 필드가 포함된 변경은 자동으로 표시가 붙고, 지정된 승인자 없이는 병합되지 않습니다.**
> 실수로 바꿨다면 그대로 두지 말고 되돌려 주세요.

### 5.1 누가 승인해야 하나

**고치는 것(푸시)은 누구나 할 수 있습니다.** 다만 **반영(병합)에 필요한 승인자**가 변경 내용에
따라 달라집니다. 제안은 자유롭게 올리시고, 승인은 아래를 따릅니다.

| 무엇을 바꿨나 | 필요한 승인 |
|---|---|
| 본문·절 제목·FAQ | 같은 부서 동료 1명 |
| 문서 새로 등록 / 폐기 | 소유 부서 **팀장** (신규는 인사팀도) |
| **`owner_dept`** (문서 주인 변경) | **넘기는 부서 팀장 + 받는 부서 팀장** |
| **`authority_level`** (규정 위계) | **인사팀장** |
| **`acl_groups`·`sensitivity`** (열람 범위) | **인사팀장 + 보안 담당자** |
| **`statutory`** (법정 항목) | **인사팀 지정 담당자** |

`statutory`만 개인이 지정되어 있습니다. 어떤 제도가 법정 최소 기준의 적용을 받는지는
**회사 전체에서 하나로 판단해야** 하고, 이 판단이 틀리면 법에 어긋난 안내가 나가기 때문입니다.

> 오탈자 수정에 팀장 승인은 필요 없습니다. 대부분의 변경은 **동료 1명 확인으로 끝납니다.**

## 6. 좋은 문서를 쓰는 요령

챗봇이 답을 잘 찾게 하는 요령입니다. 문서를 사람이 읽기에도 좋아집니다.

**① 절 제목에 사람들이 실제로 쓰는 단어를 넣으세요.**

직원은 "장비"라고 묻지 않고 "노트북"이라고 묻습니다.

- ❌ `## 장비 지급` → ✅ `## 노트북·장비 지급`
- ❌ `## 자기계발 지원` → ✅ `## 자기계발 지원 (도서 구입비·교육비)`

**② 한 절에는 한 가지만 담으세요.**

`비밀번호`가 제목에 들어간 절이 여러 개면 챗봇이 어느 절을 가리키는지 구분하지 못합니다.
실제로 "비밀번호 재설정은 어디서 하나요?"에 "90일마다 변경합니다"가 답으로 나온 적이 있습니다.

**③ 자주 묻는 질문 절을 만드세요.**

직원이 묻는 문장 그대로 적으면 챗봇이 그 답을 바로 씁니다. 가장 효과가 큽니다.

```markdown
## 자주 묻는 질문

**업무용 노트북은 어디서 받나요?**
입사 첫날 IT팀에서 받습니다. 수령할 때 자산 번호를 확인합니다.
```

**④ 답을 한 문장 안에 담으세요.**

챗봇은 문장 하나를 골라 요약으로 씁니다. 답이 두 문장에 나뉘면 반쪽만 보일 수 있습니다.

## 7. 터미널을 쓰는 경우 (개발팀 등)

```bash
git pull                                   # 최신 상태로
git switch -c dev/개발팀-합류안내-보강         # 새 브랜치
# ... 문서 수정 ...
python3 tools/validate_docs.py             # 올리기 전 스스로 검증
python3 tools/run_eval.py                  # 회귀 확인
git add prototype/data/knowledge/DEV-001-*.md
git commit -m "개발팀 합류 안내: 첫 주 순서에 계정 발급 문의처 추가"
git push -u origin HEAD                    # 이후 웹에서 MR 생성
```

`validate_docs.py`와 `run_eval.py`를 **올리기 전에 직접 돌리면** CI에서 걸리는 왕복을 줄일 수
있습니다. 두 명령 모두 인터넷 연결이 필요 없습니다.

## 8. 막혔을 때

| 상황 | 연락처 |
|---|---|
| 소스트리 설치·저장소 연결 | IT팀 |
| 검증 실패 원인을 모르겠음 | IT팀 |
| 권한(`acl_groups`)을 어떻게 설정할지 모르겠음 | 인사팀 |
| 규정 위계(`authority_level`) 판단 | 인사팀 (필요 시 법무 검토) |
| 내가 올린 변경을 되돌리고 싶음 | IT팀에 커밋 번호와 함께 요청 |

> 본 가이드의 연락처·저장소 주소는 실제 도입 시 각 회사 정보로 대체합니다.
