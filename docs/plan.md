## 0. 이 과제가 증명하려는 것

과제는 두 갈래이며, 각각 **다른 방식으로** 증명합니다.

| | 무엇을 | 증명 방식 |
|---|---|---|
| 프로토타입 | RAG 검색·권한 통제·근거 인용·가드레일 | **실행되는 시연** |
| On-premise 구축 | 사내 폐쇄 환경 배치 방안 | **설계 문서** |

프로토타입은 온프레미스 환경에서 실행되지 않습니다. 합성 문서만 사용하므로 어디에서 실행하든
실제 사내 데이터가 외부로 나가지 않으며, 외부 LLM API를 호출하지 않습니다. 온프레미스로의
전환은 코드 재작성이 아니라 **세 개 인터페이스의 구현체 교체**로 이루어지도록 설계했습니다.

## 1. 문제 정의

### 1.1 타깃 사용자

| 사용자 | 특성 | 핵심 어려움 |
|---|---|---|
| 첫 직장 신규 입사자 | 사내 제도·용어·업무 도구가 모두 낯설다 | 무엇을 언제 어디에 제출·신청·이수해야 하는지 파악하기 어렵다 |
| 경력 입사자 | 일반적 회사 경험은 있으나 해당 회사 규정과 시스템은 낯설다 | 기존 경험과 다른 사내 절차·예외를 빠르게 확인해야 한다 |

### 1.2 해결할 문제

온보딩 정보가 HR 안내문, 교육 자료, 결재 문서, 복지 공지에 흩어져 있으면 입사자는 정보를 찾느라
시간을 쓰고, 인사팀은 같은 문의를 반복 처리합니다.

이 챗봇은 단순 FAQ가 아니라 다음을 제공합니다.

- 질문 의도에 맞는 **승인된 사내 문서 검색**
- 답변마다 **근거 문서명·버전·관련 구간** 제시
- 해야 할 일, 담당 부서, 제출물, 기한을 구조화한 **다음 행동 안내**
- 권한 밖 정보·근거 없는 추정·민감정보 요청을 거절하는 **안전한 응답**

### 1.3 성공 경험

> "신규 입사자가 필요한 온보딩 절차를 질문 한 번으로 이해하고, 정확한 사내 문서 근거와
> 다음 행동까지 확인한다."

기능만으로는 부족하며 다음 비기능 경험이 필수입니다.

- **신뢰:** 답변의 근거·문서 버전·한계를 확인할 수 있다
- **통제:** 접근 권한에 맞는 문서만 검색되고 민감 정보는 노출되지 않는다
- **안정성:** 근거가 부족하면 추정하지 않고 담당 부서 안내로 전환한다
- **예측 가능성:** 질문 형식이 달라도 일관된 답변 구조를 제공한다
- **수정 가능성:** 잘못되거나 오래된 답변을 사용자가 피드백할 수 있다

## 2. MVP 범위

### 2.1 포함할 온보딩 플로우

| 플로우 | 안내 내용 | 지식 문서 |

| 계정·장비 | 계정 발급 시점, 첫 로그인, 비밀번호·화면 잠금, 노트북 수령 | OPS-003 |
| 복지 | 복지 포인트, 경조사 지원, 자기계발 지원, 식대 | HR-007 |

| 공통 사내 업무 | 비품 신청, 전자결재 절차 | OPS-001, OPS-002 |

| 문의·예외 | 담당 부서 연결, 에스컬레이션 | HR-005 |

### 2.2 건강검진 프로토타입 가정

> 아래는 **실제 회사 정책·병원·계정이 아닌 데모용 합성 가정**이며, 챗봇 화면과 지식 문서에
> 이 사실을 명시합니다.

- 대상: 입사자 **본인만** 고려하며 가족 지원은 범위에서 제외합니다
- 신규 입사자: 입사 **다음 해**부터 대상
- 계속 근로자: **2년에 1회** 대상 (첫 대상은 입사 다음 해, 이후 2년 주기)
- 예약: 지정 병원 사이트로 이동하는 **링크만** 제공하며 예약·로그인·결제는 구현하지 않습니다
- 계정: 실제 아이디·비밀번호를 저장·표시·전달하지 않습니다
- 패키지: `KMI 베이직 요금`을 예시 패키지명으로만 사용하며 실제 가격·항목으로 단정하지 않습니다

경계 케이스(12월 입사, 이직자 첫 해 등)의 판정 규칙은
[기술 설계서 §6](../prototype/docs/technical-design.md)의 결정표에 정의되어 있습니다.

### 2.3 연말정산 프로토타입 가정

- 챗봇은 가이드와 유형별 체크 항목을 **조회·요약**합니다. 홈택스 로그인·자료 제출·신청은
  구현하지 않습니다
- 신규(첫 직장) / 계속 근로자 / 이직자로 분기하며, **해당하지 않는 유형의 안내는 인용 본문에서도
  제외**합니다
- 부양가족, 공제 요건, 제도 변경은 공식 자료 확인과 담당자 검토를 거쳐 확정합니다
- 답변에 "확인 필요" 영역을 명시합니다

### 2.4 데모용 담당 부서

> 아래 연락처와 인물은 데모용 가상 정보이며 실제 담당자가 아닙니다.

- 담당 부서: 인사팀 / 담당자: 홍길동 대리 / 이메일: `hr-demo@example.com`

근거가 부족하거나 개인별 예외 판단이 필요하면 다음과 같이 안내합니다.

> 확인 가능한 문서 근거가 충분하지 않습니다. 인사팀 홍길동 대리(`hr-demo@example.com`)에게
> 확인해 주세요. 본 연락처는 해커톤 데모용 가상 정보입니다.

### 2.5 저장 정책

> **원칙:** 사용자가 **직접 저장을 선택한 것**은 저장합니다. 민감 원본 데이터와 실제 제출 파일은
> 저장하지 않습니다. 자동 수집은 최소화합니다.

| 저장함 | 저장하지 않음 |
|---|---|
| 저장한 답변 (질문·5단 구조 전체) | 주민등록번호·신분증·계좌번호·카드번호 |
| 내 할 일 (항목·출처·완료 여부) | 비밀번호·인증번호 |
| | 건강검진 결과 등 건강정보 |
| | **실제 제출 파일** (챗봇은 업로드를 받지 않습니다) |
| | 급여·인사 평가 정보 |

- 저장 항목은 **본인만** 조회하며 인사담당자·관리자도 열람할 수 없습니다
- 저장 전 민감정보 검사를 통과한 것만 저장합니다
- 출처 문서가 갱신되면 저장 항목에 갱신 안내를 표시하고, 새로 담긴 항목은 탭의 숫자를 작고 빨갛게 강조합니다
- 품질 개선용 자동 로그에는 질문 원문이 남지 않습니다 (해시와 카테고리만)

### 2.6 제외 범위

- 실제 사내 문서, 실제 개인정보, 실제 급여·건강·세무 데이터 사용
- 실제 병원 예약, 홈택스 로그인, 파일 업로드, 결재·신청의 실행
- 개인별 세무·건강 판단, 법률·의료 조언
- 인사팀 승인·정책 변경을 대신하는 자동 의사결정
- 가족 건강검진 지원 및 상세 복지 정책
- 다국어 지원과 접근성 대응 (필요성은 인정하되 이번 범위 밖으로 둡니다)

## 3. AX 서비스 구조

### 3.1 업무 분석

| 업무 | 입력 | 처리 | 판단 지점 | 승인 구조 | 병목 |
|---|---|---|---|---|---|
| 온보딩 문의 응대 | 질문, 승인 문서 | 분류 → 권한 확인 → 검색 → 근거 답변 | 근거 충분성, 민감도, 최신성 | 정책·예외는 인사팀 | 문서 분산, 반복 문의, 버전 혼선 |
| 건강검진 안내 | 입사 구분·입사일, 운영 문서 | 대상 판정 → 절차 안내 | 개인 대상 여부·예외 | 예외는 인사팀 승인 | 개인별 조건 |
| 연말정산 안내 | 고용 상태, 이직 여부, 가이드 | 유형 분류 → 준비 서류 안내 | 공제 요건·제도 변경 | 세부 판단은 공식 채널 | 규정 변경, 이직자 서류 누락 |

### 3.2 AI 역할과 제약

| 구분 | 내용 |
|---|---|
| AI 적용 영역 | 반복 문의 분류, 문서 검색, 절차 요약, 할 일 목록 추출 |
| AI 역량 | 검색(RAG), 근거 정리, 초기 분류, 근거 부족 감지 |
| **AI가 하지 않을 일** | 권한 부여, 실제 신청·결재 실행, 세무·건강 개별 판단, 정책 예외 최종 결정 |
| AI 역할 | 승인된 문서를 바탕으로 사실을 안내하고 근거·한계·다음 행동을 제시하는 안내자 |

**제약사항**

- 문서에 없는 사실을 생성하거나 개인 상황을 추론하지 않습니다
- 문서 접근 권한을 우회하지 않습니다
- 주민등록번호·계좌번호·건강검진 결과·비밀번호를 질문·저장·출력하지 않습니다
- 문서 최신성·버전이 불명확하면 확정적으로 답하지 않습니다
- 외부 서비스의 실제 로그인·신청을 대행하지 않습니다

### 3.3 휴먼 역할

| 개입 유형 | 담당 |
|---|---|
| 예외 판단 | 문서에 없는 개별 상황, 건강검진 대상 예외, 이직·공제 특이사례 |
| 최종 승인 | 지식 문서 등록·수정·폐기와 공개 범위 |
| 정책 판단 | 사내 규정과 외부 제도 변경의 반영 여부 |
| 위험 대응 | 민감정보 노출 의심, 권한 오류, 부정확 답변 조사·차단 |

## 4. 가드레일과 Fail-safe

| 위험 상황 | 자동 대응 | 휴먼 개입 |
|---|---|---|
| 권한 없는 문서 검색 | 검색 전 필터 + 반환 전 재검증. **근거 부족과 동일 문구로 응답** | 권한 부여는 기존 사내 절차로만 |
| 민감정보 입력·출력 | 입력 거부, 원문 미저장, 유형만 기록 | 보안 담당자가 오탐·사고 검토 |
| 근거 없는 답변 | 게이트 미통과 시 "확인 불가" + 담당 부서 안내 | 담당자가 문서 보강 |
| 오래된 정책 답변 | 유효기간 경과 문서는 검색 제외 | 문서 소유자가 최신본 승인 |
| 프롬프트 인젝션 | 출력이 인용 문서의 부분 문자열로 제한되어 **구조적으로 무력** | 보안 담당자가 패턴 분석 |
| 서비스 장애 | 추정 금지, 장애 안내와 담당 부서 연결 | 운영자 복구·원인 분석 |

**신뢰성 필수 기능**

- **설명 가능성** — 답변마다 인용 문서명, 버전, 관련 구간, 발췌를 표시
- **수정 가능성** — 피드백 수집
- **통제 가능성** — 승인 없는 문서는 색인되지 않으며 권한별로 결과가 달라짐
- **예측 가능성** — `요약 → 해야 할 일 → 참고 문서 → 주의·예외 → 담당 부서` 고정 구조
- **안정성** — 인용 없는 답변을 허용하지 않고 실패 시 안전하게 에스컬레이션

| **HR-007** | 복지 제도 안내 | 인사팀 | internal | 전 직원 |
| **REG-001** | 취업규칙 발췌 (규정 · 취업규칙) | 인사팀 | internal | 전 직원 |
| **REG-002** | 개발팀 근무 지침 (규정 · 부서지침) | 개발팀 | internal | **개발팀만** |
| **REG-003** | 취업규칙 개정안 (2027 시행 예정) | 인사팀 | internal | 전 직원 (시행 전) |

HR-006과 DEV-001은 권한 통제를 실제로 시연하기 위해 추가했습니다. 초기 7종은 모두 전 직원
공개여서 "권한 밖 문서 차단"을 보여줄 대상이 없었습니다. DEV-001은 **같은 질문에 소속에 따라
결과가 갈리는** 시연을 가능하게 합니다.

문서 메타데이터 스키마와 검증 규칙은
[기술 설계서 §3](../prototype/docs/technical-design.md)에 정의되어 있습니다.

### 인사담당자 콘텐츠 운영

인사담당자는 답변을 직접 고치는 사람이 아니라, 챗봇이 참조하는 **승인된 지식 문서와 답변 정책을
관리하는 콘텐츠 오너**입니다. 이렇게 해야 근거·최신성·책임 소재가 유지됩니다.

```text
[초안 작성] → [카테고리·대상·민감도·유효기간 입력] → [정책 소유자 검토] → [승인]
  → [색인 반영] → [답변에 문서 버전과 근거로 노출] → [피드백·만료 검토] → [수정 또는 폐기]
```

- **긴급 수정:** 잘못된 정책이나 민감정보 노출이 의심되면 해당 문서를 즉시 검색에서 비활성화합니다
- **시즌 문서:** 연말정산·건강검진은 시즌 시작 전 유효기간·변경점·외부 링크를 검토·승인합니다
- **개인화 정보:** 인사담당자는 개인 정보를 챗봇 문서에 작성하지 않습니다

문서 상태 전이도는 [이용 가이드 §7](./user-guide.md)에 있습니다.

## 7. 구현 결과

구현 상세는 [기술 설계서](../prototype/docs/technical-design.md)에 있습니다. 기획 관점에서
확인할 결과만 정리합니다.

| 설계 의도 | 구현 방식 | 확인 |
|---|---|---|
| 근거 없는 답변 금지 | 답변의 모든 문장이 인용 문서의 부분 문자열이어야 하는 불변 조건을 코드가 강제 | 근거 이탈 0.000 |
| 프롬프트 인젝션 방어 | 위 불변 조건으로 **구조적으로 무력화** | G-027 통과 |
| 권한 통제 | 검색 전·답변 반환 전 2회 검증, 차단 시 근거 부족과 동일 문구 | 차단률 1.000 |
| 개인화 경계 | 결정표로 판정하고 파생 결과만 노출, 다른 유형의 내용은 인용에서 제외 | G-011~G-016 통과 |
| 민감정보 | 차단 / 마스킹 / 정상 처리 3단 분리로 제도 문의를 막지 않음 | G-024~G-026 통과 |
| 임계값의 근거 | 골든셋 점수 분포에서 분리 구간을 찾아 산출 | `tools/tune_thresholds.py` |

### 구현 중 발견해 고친 것

문서만으로는 드러나지 않고 실제로 만들어 봐야 나온 결함들입니다.

1. **bi-gram이 내용어를 압도** — 소규모 코퍼스에서 TF-IDF 공간이 bi-gram에 지배되어 정상 질문과
   무관한 질문이 같은 점수를 받았습니다. 절 제목을 가중해 해결했습니다
2. **SVD가 잡음을 추가** — 43청크 규모에서 차원 축소가 이득 없이 분리도만 떨어뜨렸습니다
3. **FAQ 절이 본문 절을 가림** — 질문을 되풀이하는 FAQ가 정작 답이 있는 절보다 높게 잡혔습니다
4. **개인화가 메시지만 분기** — 계속 근로자에게 이직자 서류 안내가 인용 본문에 그대로 노출됐습니다
5. **발행일이 같다는 이유로 문서 충돌 오판** — 서로 다른 주제의 문서를 충돌로 표시했습니다

## 8. 지속 운영

1. 문서 소유 부서가 갱신·유효기간·폐기를 관리합니다
2. 승인된 문서만 색인에 반영합니다
3. 검색 실패·근거 부족·부정확 피드백을 주기적으로 검토합니다
4. 문서 보강, 청크 전략, 검색 가중치, 가드레일을 변경 관리 절차로 개선합니다
5. 변경 전후 지표를 골든셋으로 비교합니다
6. 권한 오류·민감정보 노출 의심은 즉시 차단하고 보안·HR이 조사합니다
