# On-premise RAG 챗봇 구축 설계

| 항목 | 내용 |
|---|---|
| 문서 ID | DOC-003 |
| 버전 | v2.4 |
| 개정일 | 2026-09-02 |
| 목적 | 온보딩 RAG 챗봇을 사내 폐쇄 환경에 구축하는 방안을 설계한다 |
| 관련 문서 | [`../prototype/docs/technical-design.md`](../prototype/docs/technical-design.md) · [`../docs/user-guide.md`](../docs/user-guide.md) · [`../docs/document-admin-guide.md`](../docs/document-admin-guide.md) · [`../docs/plan.md`](../docs/plan.md) |

> **이 문서의 위치:** 프로토타입은 **동작으로** 증명하고, On-premise 구축은 **설계로** 증명한다.
> 프로토타입은 온프레미스 환경에서 실행되지 않는다. 이 문서는 그 전환을 어떻게 하는지를 다룬다.
>
> **핵심 원칙:** 사내 문서 원문, 사용자 질문, 임베딩, 추론 결과가 외부 LLM API나 외부 벡터 DB로
> 전송되지 않도록 구성한다.

## 0. 프로토타입과 목표 운영 환경

| | 프로토타입 (구현 완료) | 목표 운영 환경 (이 문서) |
|---|---|---|
| 증명 방식 | 실행되는 시연 | 설계 문서 |
| 배포 위치 | 로컬 / 일반 호스팅 | 사내망 또는 통제된 폐쇄망 |
| 지식 데이터 | 합성 온보딩 문서 14종 (안내문 11 + 규정 3) | 승인된 실제 사내 문서 |
| 인증 | 사번 선택 화면 | 사내 SSO + 서버측 RBAC |
| 답변 생성 | 추출 기반 (근거 정리형) | 사내 LLM 추론 서버 |
| 임베딩 | 코퍼스 학습형 TF-IDF | 사내 임베딩 서버 |
| 외부 API 호출 | 없음 | 없음 |

### 전환 경계는 코드에 실재한다

설계 문서의 주장이 공허하지 않으려면 전환 지점이 코드에 있어야 한다. 프로토타입은 세 개의
인터페이스로 이 경계를 구현했다.

| 계층 | 전환 시 교체 대상 | 코드 위치 |
|---|---|---|
| 임베딩 | `EmbeddingBackend` 구현체 | `app/retrieval/embedder.py` |
| 답변 생성 | `ANSWER_BACKEND` 환경변수 (extractive ↔ llm) | `app/answer/llm.py` **구현됨** |
| 인증 | 데모 로그인 → SSO | `app/main.py`, `app/session.py` |

검색·권한 판정·가드레일·답변 구조화는 **전환해도 바뀌지 않는다.**

## 1. 아키텍처

### 1.1 논리 구성

```text
[사내 사용자 브라우저]
   │  사내망 HTTPS
   ▼
[리버스 프록시 / TLS 종단]          ← 보안 헤더, 요청 제한, 접근 로그
   │
   ▼
[챗봇 UI + API (RAG 오케스트레이터)]
   ├─ 입력 검증 · 민감정보 검사 · 정책 검사
   ├─ 권한 필터 기반 검색 ─────────► [벡터 DB]  (ACL 메타데이터 포함)
   │                          └──► [BM25 색인]
   ├─ 근거 충분성 판정
   ├─ 임베딩 요청 ─────────────────► [사내 임베딩 서버]
   ├─ 답변 생성 요청 ───────────────► [사내 LLM 추론 서버]
   └─ 답변 검증 (인용 · 권한 재검증 · 민감정보)
   │
   ▼
[권한 정책 서비스] ◄── [사내 SSO / IdP]     [문서 저장소]
                                            └─ [문서 수집·승인·색인 파이프라인]
[감사 로그 · 모니터링]  ← 최소 수집 · 접근 통제 · 보존 정책
```

### 1.2 네트워크 구간 분리

| 구간 | 배치 | 인바운드 | 아웃바운드 |
|---|---|---|---|
| DMZ-사내 | 리버스 프록시 | 사내 사용자 443 | 앱 구간만 |
| 앱 | 챗봇 UI/API | 프록시에서만 | 데이터·모델 구간 |
| 모델 | LLM · 임베딩 서버 | 앱 구간에서만 | **인터넷 egress 차단** |
| 데이터 | 벡터 DB · 문서 저장소 · RDB | 앱 구간에서만 | **인터넷 egress 차단** |
| 관리 | 색인 파이프라인 · 운영 콘솔 | 관리자 네트워크에서만 | 내부 레지스트리만 |

일반 사용자 네트워크에서 모델·데이터·관리 구간에 직접 접근할 수 없다.

## 2. 구성 요소와 자원 산정 (D1)

### 2.1 프로토타입 실측값

아래는 프로토타입을 실제로 측정한 값이다. 추정이 아니라 측정 결과이며, 운영 규모 산정의 기준선이다.

| 항목 | 측정값 | 조건 |
|---|---|---|
| 지식 문서 | 42.5 KB / 14종 | 마크다운 원본 |
| 청크 수 | 78개 | 안내문은 절 단위, 규정은 **조·항 단위** |
| 벡터 저장 | 148.9 KB | TF-IDF 희소 표현 |
| FAQ 색인 | 35쌍 | 질문-답 직접 매칭용 (§4.8) |
| 부팅 시간 (색인 포함) | 286 ms | 전체 재색인 포함 |
| 상주 메모리 | 35 MB | Python + numpy (외부 ML 라이브러리 없음) |
| 응답 지연 P50 | 6.3 ms | 추출 기반, LLM 미사용 |
| 응답 지연 P95 | 7.5 ms | 저장소 I/O 포함 |

**해석:** 검색·권한 판정·답변 구조화는 **비용이 거의 없다.** 운영 환경의 자원 산정은 사실상
**LLM 추론과 임베딩 모델이 전부 결정한다.**

### 2.2 운영 환경 자원 산정

문서 규모를 실측값에서 선형 확장해 추정한다.

| 지식 규모 | 예상 청크 | 임베딩 저장 (1024dim, float32) | 벡터 DB 메모리 |
|---|---|---|---|
| 문서 100종 (약 300KB) | 약 500 | 약 2 MB | 수십 MB |
| 문서 1,000종 (약 3MB) | 약 5,000 | 약 20 MB | 수백 MB |
| 문서 10,000종 (약 30MB) | 약 50,000 | 약 200 MB | 1~2 GB |

→ **벡터 저장은 병목이 아니다.** 1만 종 규모에서도 일반적인 서버 메모리로 충분하다.

**LLM 추론 서버 (모델 크기별)**

| 모델 규모 | 정밀도 | 가중치 VRAM | KV 캐시 여유 | 권장 GPU |
|---|---|---|---|---|
| 7~8B | INT4 양자화 | 약 5 GB | +3 GB | 16GB 1장 |
| 7~8B | FP16 | 약 16 GB | +6 GB | 24GB 1장 |
| 14B | INT4 | 약 9 GB | +5 GB | 24GB 1장 |
| 32B | INT4 | 약 20 GB | +8 GB | 48GB 1장 또는 24GB 2장 |

**임베딩 서버:** 소형 다국어 모델(100~300M)은 CPU로도 동작하며 GPU 사용 시 1~2 GB VRAM이면 충분하다.

**동시 사용자 대비 산정 (500명 조직 가정)**

| 항목 | 가정 | 산정 |
|---|---|---|
| 전체 직원 | 500명 | — |
| 일 활성 사용자 | 15% | 75명 |
| 1인당 일 질의 | 3회 | 225회/일 |
| 피크 집중 | 업무시간 8h 중 2h에 50% | 약 1.0 QPS |
| LLM 응답 시간 | 스트리밍 첫 토큰 1초, 완료 5초 | — |
| 필요 동시 처리 | 1.0 QPS × 5초 | 약 5 동시 요청 |

→ **7~8B INT4 모델 + 24GB GPU 1장으로 500명 조직을 감당할 수 있다.** GPU 이중화는 가용성을 위한
것이지 처리량 때문이 아니다.

### 2.3 서버 구성 권장안

| 역할 | CPU | RAM | 디스크 | GPU |
|---|---|---|---|---|
| 앱 (UI/API/오케스트레이터) | 4 vCPU | 8 GB | 50 GB | — |
| 임베딩 서버 | 4 vCPU | 8 GB | 30 GB | 선택 (없어도 동작) |
| LLM 추론 서버 | 8 vCPU | 32 GB | 200 GB (모델 파일) | 24GB 1장 |
| 벡터 DB + RDB | 4 vCPU | 16 GB | 200 GB (SSD) | — |
| 색인 파이프라인 | 4 vCPU | 8 GB | 100 GB | — |

> 앱 계층의 실측 상주 메모리는 **35MB**다. 위 사양은 동시 요청과 운영 여유를 감안한 값이며,
> 실제 병목은 앱이 아니라 LLM 추론이다.

소규모 도입은 앱·임베딩·벡터 DB를 한 서버에 합치고 LLM 서버만 분리해도 된다.

## 3. 컨테이너 구성 (D2)

### 3.1 구성표

| 서비스 | 이미지 | 포트 | 볼륨 | 네트워크 | egress |
|---|---|---|---|---|---|
| `proxy` | nginx (내부 미러) | 443 | TLS 인증서 (읽기 전용) | dmz, app | 없음 |
| `api` | 자체 빌드 (Python 3.11) | 8000 | 설정 (읽기 전용) | app, data, model | 없음 |
| `embedder` | 자체 빌드 + 모델 파일 | 8001 | 모델 (읽기 전용) | model | **차단** |
| `llm` | vLLM 또는 동등 | 8002 | 모델 (읽기 전용) | model | **차단** |
| `vectordb` | 벡터 DB | 6333 | 데이터 (영속) | data | **차단** |
| `db` | PostgreSQL | 5432 | 데이터 (영속) | data | **차단** |
| `indexer` | 자체 빌드 | — | 문서 저장소, 데이터 | data, model, admin | 내부 레지스트리만 |

### 3.2 배치 원칙

- 모든 이미지는 **내부 레지스트리에서만** 가져온다. 실행 시점의 외부 pull을 금지한다.
- `embedder`·`llm`·`vectordb`·`db`는 인터넷 egress를 기본 차단한다. 모델 파일은 이미지 또는
  마운트 볼륨으로 미리 넣는다.
- 컨테이너는 비-root 사용자로 실행하고 루트 파일시스템을 읽기 전용으로 둔다. 쓰기가 필요한
  경로만 볼륨으로 연다.
- 비밀값은 이미지에 넣지 않고 오케스트레이터의 시크릿으로 주입한다.
- 서비스 간 통신은 필요한 포트만 열고 mTLS 또는 내부 인증을 적용한다.

### 3.3 헬스체크와 기동 순서

```text
db, vectordb  →  embedder, llm  →  indexer(최초 색인)  →  api  →  proxy
```

`api`는 `embedder`·`llm`·`vectordb`가 준비되기 전에는 준비 상태를 보고하지 않는다.
기동 실패 시 추정 답변을 내지 않고 장애 안내로 전환한다.

## 4. 데이터 흐름과 보안 경계

### 4.1 문서 등록

```text
[인사담당자 초안] → [카테고리·대상·ACL·민감도·유효기간 입력] → [검토·승인]
  → [문서 파싱 · 악성 파일 검사] → [청크화 · 임베딩] → [벡터 DB 색인] → [검색 가능]
```

- 승인 전 문서는 검색 결과에 절대 포함되지 않는다. 프로토타입은 이를 `status != published`이면
  색인하지 않는 것으로 구현했고, 필수 필드 누락은 경고가 아니라 **색인 실패**로 처리한다.
- 변경·폐기 시 이전 버전과 변경 사유를 보존하고, 폐기 문서는 즉시 검색에서 제외한다.
- 개인 프로필, 계좌·신분증·건강정보, 개인별 신청 상태는 청크나 벡터 DB에 넣지 않는다.

### 4.2 질문·답변

```text
[질문] → [인증·역할 확인] → [입력 검증] → [민감정보 검사]
  → [★1차 권한 필터] → [하이브리드 검색] → [근거 충분성 판정]
  → [답변 생성] → [★2차 권한 재검증] → [출력 검사] → [답변 + 근거 + 다음 행동]
```

권한은 **검색 전과 답변 반환 전 두 번** 확인한다. 프로토타입에 두 지점 모두 구현되어 있다.

### 4.3 개인화 경계

공통 온보딩 문서만 RAG 지식베이스로 관리하고, 개인화는 별도 정책 서비스에서 최소 속성만 조회해
분기한다. **이 문서가 개인화 원칙의 단일 출처다.**

| 허용 속성 | 용도 |
|---|---|
| 사번 | 식별용. 화면에는 `12****`로 마스킹 |
| 입사일 | 건강검진·입사 절차 대상 여부 계산 |
| 신규/계속/이직 구분 | 안내 문서·체크 항목 분기 |
| 소속·역할 | 접근 가능 문서 필터 |

- 개인 원본값은 벡터 DB에 넣지 않고 LLM 프롬프트에도 불필요하게 전달하지 않는다.
- 챗봇에는 "현재 대상입니다/아닙니다" 같은 **파생된 결과만** 제공한다.
- 어떤 조건으로 판정했는지 사용자에게 한 줄로 밝힌다.
- HR·관리자는 업무상 필요한 최소 범위만 열람하고 조회 목적·대상·시각을 감사한다.
- **사용자가 직접 저장한 항목**(북마크·저장한 답변·체크리스트)은 본인만 조회하며, HR·관리자도
  열람할 수 없다. 저장 전 민감정보 검사를 통과한 것만 저장한다.

### 4.4 답변 품질 기법과 LLM 의존도 ★

답변 품질을 올리는 방법이 전부 LLM을 필요로 하는 것은 아니다. 오히려 **대부분은 아니다.**
이 구분이 온프레미스에서 중요한 이유는, LLM이 필요한 순간 §2의 GPU 자원 산정과 §5의 모델 반입
절차, 그리고 인용 검증 방식의 재설계가 **한꺼번에** 따라오기 때문이다.

| 기법 | 하는 일 | GPU | 상태 |
|---|---|:---:|---|
| 추출 기반 답변 구성 | 원문 문장을 골라 5단 구조로 조립 | — | 구현 |
| 질의 유형 판별 | 절차형·사실확인형을 구분해 답변 범위를 좁힘 | — | 구현 |
| 미지 주제어 게이트 (G5) | 주제어가 지식베이스에 없으면 점수와 무관하게 차단 | — | 구현 |
| 개인화 결정표 | 규칙 테이블로 대상 여부 판정 | — | 구현 |
| 문서 구조 정비 | 절 제목·FAQ를 사용자 어휘로 교정 | — | 운영 작업 |
| **FAQ 고신뢰 매칭** | 문서의 Q/A 쌍을 파싱해 질문끼리 직접 대조 | — | **구현** |
| 어미 처리 개선 | 토큰화 정확도를 올려 검색·게이트·매칭을 동시 개선 | — | 설계 |
| 표 행 단위 추출 | 표에서 질문에 해당하는 행만 인용 | — | 설계 |
| IDF 가중 문장 선택 | 희귀어(`1월`)를 흔한 말(`지급`)보다 무겁게 | — | 설계 |
| 별칭 사전 (`aliases`) | `사무용품↔비품` 같은 어휘 불일치 완화 | — | 설계 |
| ⚠️ **흩어진 사실 병합** | 두 문장에 나뉜 답을 한 문장으로 합침 | **필요** | **구현** (§7.5 기술설계서) |
| ⚠️ **자연어 재작성** | 문서 어투를 대화 어투로 바꿈 | **필요** | 범위 밖 |

> **⚠️ 표시의 의미는 "외부로 나간다"가 아니다.** 사내 추론 서버를 쓰면 이 둘도 외부 통신은
> 없다. ⚠️는 **비용 구조가 달라진다**는 뜻이다 — GPU 자원(§2), 모델 반입·해시 검증(§5),
> 그리고 아래의 검증 재설계가 함께 필요해진다.

**⚠️ 항목이 깨뜨리는 것 — 인용 검증**

현재는 "답변의 모든 문장이 인용 청크 원문의 부분 문자열인가"를 검사해 할루시네이션을
**구조적으로** 막는다. 그런데 두 문장을 합치면 그 합친 문장은 원문에 없으므로 이 검사를
통과하지 못한다. 따라서 ⚠️ 항목을 도입할 때는 검증을 다음으로 교체해야 한다.

- 합친 문장에 등장하는 **숫자·날짜·금액·기한이 전부 원문에 존재하는가**
- 원문에 없는 고유명사·부서명·시스템명이 새로 생기지 않았는가
- 인용 문서·절이 실제로 그 사실을 담고 있는가

즉 ⚠️ 항목은 기능 추가가 아니라 **안전 보장 방식의 교체**다. 검증 설계 없이 먼저 붙이면
"지어내지 않는다"는 이 시스템의 핵심 주장이 사라진다.

**우선순위:** ⚠️가 없는 항목을 먼저 소진한다. 실측상 현재 남은 답변 실패의 **다수는 검색
단계에서 막힌 것**이라, 병합 기능을 붙여도 해결되지 않는다 — LLM이 애초에 그 텍스트를 받지
못하기 때문이다. ⚠️ 항목은 위 기법을 모두 적용하고도 남는, **정말로 여러 문장에 흩어진
사실**에만 쓴다.

### 4.5 문서 정비 절차 ★

RAG 도입에서 가장 큰 비용은 모델도 인프라도 아니고 **기존 자료를 이 형식으로 옮기는 일**이다.
이 절은 그 작업을 어떻게 나누고, 무엇이 자동화되며, 정리 과정 자체가 폐쇄망 원칙을 깨지 않게
하는 방법을 정의한다.

#### 4.5.1 세 층위 — 자동화 가능성이 전혀 다르다

"포맷 변환"으로 뭉뚱그리면 규모를 잘못 잡는다. 실제로는 성격이 다른 세 겹이다.

| 층 | 하는 일 | 자동화 | 비용 |
|---|---|---|---|
| **본문 변환** | Word·PDF·위키 → 마크다운 | 결정적 도구(pandoc 등) | 낮음 |
| **구조 정비** | 절 나누기, 절 제목을 사용자 어휘로, FAQ 추출 | 반자동 (사람 검수) | 중간 |
| **메타데이터 부여** | `acl_groups`·`sensitivity`·`authority_level`·`statutory` | **불가능** | 높음 |

**세 번째가 진짜 일이다.** 메타데이터는 데이터가 아니라 **결정**이다. 회사에 있는 어떤 파일에도
"이 문서는 개발팀만 볼 수 있다"고 적혀 있지 않다. 지금까지 폴더 권한이나 암묵적 합의로
굴러온 것을 처음으로 명시하는 작업이며, 자동으로 만들 수 없다.

이 프로젝트의 핵심 주장인 "권한 밖 문서는 존재조차 알리지 않는다"는 **문서마다 사람이
판단해 붙인 메타데이터 위에서만 성립한다.** 회사가 이 작업을 하지 않으면 ACL 보장을 할 수 없다.

**두 번째 층의 효과는 실측되어 있다.** 구조 정비는 "읽기 좋게"가 아니라 **검색이 골라내기 좋게**
만드는 작업이다.

| 조치 | 실측 결과 |
|---|---|
| 절 제목을 사용자 어휘로 (`장비 지급` → `노트북·장비 지급`) | 사라졌던 게이트 분리 구간이 **-0.0668 → +0.0484**로 복구 |
| 한 절에 한 주제 (`비밀번호 재설정`을 독립 절로 분리) | "재설정은 어디서?"에 `90일마다 변경`이 답으로 나오던 것이 해소 |
| FAQ 항목 추가 | 질문-답 직접 매칭(§4.8 기술설계서)으로 3개 질의가 추가 해결 |

절 제목은 검색에서 **3배 가중**된다. 문서 손질이 임계값 조정보다 값싸고 확실한 개선 수단인
이유다.

#### 4.5.2 규정 문서의 추가 정비

내규·업무규정은 안내문과 다른 정비가 필요하다. 상세 규칙은 기술설계서 §3.3에 있고, 정비
관점의 요점은 다음과 같다.

| 항목 | 누가 정하나 | 틀리면 |
|---|---|---|
| `doc_type: 규정` | 문서 담당자 | 조문이 문장 경계로 잘려 **단서가 사라진 조문**이 인용된다 |
| `authority_level` | **인사팀 (법무 검토 권장)** | 부서 지침이 취업규칙을 이긴다 |
| `effective_from` | 문서 담당자 (부칙에서 확인) | **시행 전 개정안**으로 답한다 |
| `statutory` | **인사팀** | 법정 기준 미달 고지가 빠져 위법한 안내가 나간다 |

**조문 구조는 변환 단계에서 보존해야 한다.** 원본이 HWP·PDF일 때 "제12조 ③"의 항 기호(`①②③`)가
글머리표나 일반 숫자로 바뀌면 조문 청킹이 동작하지 않는다. 변환 후 **항 기호 보존 여부를 반드시
확인**한다.

#### 4.5.3 정리 작업의 네트워크 통제 ★

**"사내 데이터가 외부로 나가지 않는다"를 주장하는 시스템이, 그 데이터를 정리하려고 외부 API를
쓰면 주장이 무너진다.** 정비 과정도 운영과 같은 통제를 받는다.

| 통제 | 내용 |
|---|---|
| 외부 통신 지점 | **반입 게이트 1곳으로 한정** (§5). 모델·패키지를 해시 검증 후 내부 레지스트리로 |
| 정리 서버 egress | **차단.** 내부 레지스트리만 허용 |
| 모델 이름 화이트리스트 | 클라우드로 라우팅되는 모델명(예: `-cloud` 접미사)을 **금지 목록**으로 관리 |
| 계정 로그인 | 정리 서버에서 외부 모델 서비스에 로그인하지 않는다 |
| 텔레메트리 | 사용하는 도구의 기본 텔레메트리를 **명시적으로 끈다** (opt-out인 도구가 있다) |

> **설정으로는 증명할 수 없다.** 로컬 전용이던 도구가 버전업으로 클라우드 경로를 갖는 일이
> 실제로 있다. 기본값은 바뀌므로, 폐쇄망 주장은 **egress 차단으로** 증명한다. 모델명
> 화이트리스트는 실수 방지용 2차 장치다.

#### 4.5.4 중앙 정리 에이전트

정리는 **한 곳에서** 한다. GPU 서버가 1대면 되고(정리는 상시 부하가 아니라 배치), 절 분할
규칙을 한 곳에서 관리하며, 누가 무엇을 바꿨는지 감사 로그가 한곳에 남기 때문이다. 부서마다
각자 돌리면 포맷이 갈리고 통제가 안 된다.

```text
[반입 게이트]  ← 외부 통신은 여기 1회뿐 (모델·패키지, 해시 검증)
      │  이후 egress 차단
      ▼
[정리 에이전트 서버]  내부망 · 아웃바운드 없음
   원본 업로드 → 변환 → 절 분할·제목·FAQ·front-matter **초안 제안**
      │
      ▼
[담당자 검수]  ← acl_groups · authority_level · statutory 는 반드시 사람이 확정
      │
      ▼
[승인 → 색인]
```

**핵심 안전장치: LLM에게 본문을 다시 쓰게 하지 않는다.**

정리 에이전트에게 허용하는 일은 셋뿐이다.

1. 절·조문 경계 제안
2. 절 제목 제안 (사용자 어휘로)
3. front-matter 후보 제시

**본문은 원문 문자열 그대로 둔다.** 그러면 모델이 틀려도 문서가 왜곡되지 않는다 — 잘못된
제목이 붙을 뿐이고 검수에서 잡힌다. 챗봇의 답변 생성이 "원문의 부분 문자열만 쓴다"는 불변
조건을 지키는 것과 같은 원리를, 정비 단계에도 적용한다.

#### 4.5.5 검수를 빠르게 만드는 법

사람이 병목이므로 **타이핑이 아니라 승인만** 하게 만든다.

- 메타데이터는 **폴더 구조에서 상당수 유추**된다. `/인사팀/…` → `owner_dept: 인사팀`. 사람은 예외만 고친다
- `acl_groups` 기본값을 **소유 부서**로 두고, 전사 공개로 올릴 때만 결재를 받는다 → 안전한 쪽이 기본이 된다
- 배치로 돌려놓고 사람은 **diff만** 본다. 문서를 처음부터 읽게 하지 않는다
- 부서당 담당자 1명을 지정한다. 메타데이터는 결정이므로 주인이 있어야 한다
- `authority_level`과 `statutory`는 **부서 담당자가 아니라 인사팀이** 확정한다 (위계·법정 사항은 전사 일관성이 필요)

#### 4.5.6 착수 우선순위 — 문서가 아니라 질문에서 출발

사내 문서 전체를 변환하려 들면 끝나지 않는다. **신규 입사자가 실제로 많이 묻는 질문 30~50개를
먼저 모으고, 그 답이 있는 문서만 정비한다.**

이 프로토타입이 그 근거다. **문서 14종이 골든셋 48문항을 답한다.** 온보딩 질문의 분포는 좁고,
초기에 필요한 문서 수는 예상보다 훨씬 적다.

#### 4.5.7 문서 정비 체크리스트

문서 하나를 색인에 넣기 전 확인한다.

- [ ] 필수 front-matter가 모두 있는가 (누락은 경고가 아니라 **색인 실패**)
- [ ] `acl_groups`를 **사람이** 판단해 붙였는가. 기본값을 그대로 둔 것은 아닌가
- [ ] 절 제목이 **사용자가 실제로 쓰는 단어**인가 (`장비 지급` vs `노트북 지급`)
- [ ] 한 절이 **한 주제**만 다루는가. 제목이 겹치는 절이 같은 문서에 있지 않은가
- [ ] 자주 묻는 질문 절에 **실제 질문 형태**로 항목이 있는가
- [ ] (규정) `doc_type`·`authority_level`·`effective_from`을 선언했는가
- [ ] (규정) 변환 후에도 **항 기호(`①②③`)가 보존**되었는가
- [ ] (규정) 법정 항목이면 `statutory`에 선언했는가
- [ ] 실제 개인정보·실재 연락처·실재 도메인이 없는가
- [ ] **색인 후 골든 문항을 추가하고 §11.4 튜닝 절차를 다시 실행했는가**

마지막 항목을 건너뛰면 조용히 망가진다. 실제로 문서 2종을 추가했을 때 게이트 분리 구간이
사라졌고, 임계값이 아니라 **문서를 고쳐서** 복구했다.

### 4.6 문서 편집과 감사 로그 ★

#### 4.6.1 폴더 직접 수정은 허용하지 않는다

인사담당자가 문서 디렉터리에 들어가 파일을 고치는 방식은 세 가지가 동시에 깨진다.

| 깨지는 것 | 구체적으로 |
|---|---|
| **승인 절차** | 본인이 `status: published`를 직접 붙일 수 있다. 검토 없이 발행된다 |
| **권한 통제** | `acl_groups`를 `dept:개발팀`에서 `all_employees`로 바꿔도 아무 검증이 없다. **인사평가 문서가 전 직원에게 열려도 아무도 모른다** |
| **추적** | 누가 언제 무엇을 바꿨는지 남지 않는다. 개인정보를 다루는 시스템에서 이는 규정 문제다 |

규정 문서가 들어오면 여기에 하나가 더 붙는다. `authority_level`을 낮추면 **부서 지침이
취업규칙을 이기게** 되고, `statutory`를 지우면 **법정 기준 고지가 사라진다.** 둘 다 화면에
아무 표시 없이 잘못된 안내로 바뀐다.

#### 4.6.2 Git을 원본으로 둔다

문서가 마크다운이므로 형상관리가 자연스럽게 맞는다. 폐쇄망에 사내 GitLab이 이미 있으면
**추가 개발 없이** 검토·이력·롤백이 전부 해결된다.

| 필요한 것 | 편집 UI를 직접 만들면 | **Git 기반** |
|---|---|---|
| 검토·승인 | 직접 구현 | **MR = 검토, 승인자 = 리뷰어** |
| 변경 이력 | 직접 구현 | **커밋이 곧 감사 로그** (누가·언제·무엇을·왜) |
| 롤백 | 직접 구현 | `git revert` |
| 발행 게이트 | 직접 구현 | **CI 검증 통과 시에만 병합** |
| 개발 비용 | 큼 | 사내 GitLab이 있으면 거의 0 |
| 담당자 진입장벽 | 낮음 | 높음 (교육 필요) |

**권장 구조:** Git을 원본(single source of truth)으로 두고, 인사담당자용 편집 화면은 그 위에
**얇게** 올린다. 화면에서 저장하면 커밋이 생기고, 같은 감사 이력에 합류한다. 화면이 없어도
시스템은 완전하게 동작한다.

```text
[초안 브랜치] → [MR 생성] → [CI 검증] → [리뷰어 승인] → [main 병합] → [자동 색인]
                                │                                        │
                          실패 시 병합 차단                          커밋 = 감사 로그
```

**자기 승인 금지.** 작성자와 승인자는 달라야 한다. MR 작성자가 자기 MR을 승인할 수 없도록
저장소 설정으로 강제한다. `authority_level`·`statutory` 변경은 **인사팀 승인**을 추가로 받는다.

#### 4.6.3 CI 검증 게이트 — 색인 전에 막는다

병합 전 자동 실행하며, 하나라도 실패하면 병합할 수 없다. 프로토타입에 `tools/validate_docs.py`로
구현되어 있다.

| 검사 | 실패 시 |
|---|---|
| front-matter 필수 필드·값 범위 | 병합 차단 |
| `doc_type: 규정`인데 `authority_level` 미선언 | 병합 차단 |
| `demo_assumption: true`인데 본문 고지 없음 | 병합 차단 |
| `effective_from`·`valid_until` 형식·순서 | 병합 차단 |
| `doc_id` 중복, 파일명·`doc_id` 불일치 | 병합 차단 |
| 규정인데 항 기호(`①②③`)가 소실됨 | 경고 (변환 사고 조기 발견) |
| **골든셋 회귀** | 병합 차단 |
| **게이트 분리 구간 소실** (§11.4 기술설계서) | 경고 후 문서 보강 요구 |

마지막 두 개가 핵심이다. 문서 하나를 바꿨을 뿐인데 **다른 질문의 답이 틀어지는 일이 실제로
발생**하므로, 사람이 기억해서 돌리는 것이 아니라 병합 조건으로 강제한다.

#### 4.6.4 감사 로그 등급

문서 변경을 한 등급으로 뭉뚱그리면 권한 사고가 본문 오탈자 수정과 같은 줄에 묻힌다.

| 등급 | 이벤트 | 보존 | 알림 |
|---|---|---|---|
| **최고** | `acl_groups` · `sensitivity` · `authority_level` · `statutory` 변경 | **3년** | 보안 담당자에게 **즉시 통보** |
| 높음 | `status` 전이(발행·폐기), `effective_from` 변경, 문서 삭제 | 1년 | 일일 요약 |
| 보통 | 본문·절 제목 수정, 버전 증가 | 1년 | — |
| 열람 | 관리자의 문서 조회, 문서 목록 조회 | 90일 | — |

각 항목에 반드시 남길 필드:

- 누가(사번) · 언제 · 어느 문서 · 어느 버전 → 어느 버전
- **변경 내용 diff** — "무엇을 바꿨는지"가 없으면 로그가 무의미하다
- `status` 전이와 **승인자** — 자기 문서를 자기가 승인했는지 사후 검출 가능해야 한다
- 최고 등급은 **변경 전후 값을 명시적으로** 기록 (`dept:개발팀` → `all_employees`)

#### 4.6.5 열람 로그

현재 프로토타입은 답변에 **인용된 문서 ID**만 남긴다. 운영에서는 다음을 추가한다.

- 문서 목록 조회 (누가 어떤 범위를 열람했는지)
- 관리자·인사담당자의 개별 문서 열람 — 업무상 필요 범위를 넘는 조회를 사후 확인하기 위함
- 권한 거부 이벤트 (이미 기록 중)

**질문 원문은 여전히 남기지 않는다**(§6.2). 열람 로그는 "누가 무엇에 접근했는가"이지 "무엇을
물었는가"가 아니다.

### 4.7 CI/CD — 병합하면 자동 배포 ★

기본 모델은 **"소유 부서가 푸시하고, 병합되면 자동 배포"**가 맞다. 다만 예외가 하나 있다.

#### 4.7.1 권한 통제는 푸시가 아니라 승인에 건다 ★

**Git의 푸시 권한은 브랜치 단위이지 필드 단위가 아니다.** "이 사람만 `statutory`를 바꿀 수
있게" 같은 설정은 형상관리 도구에 존재하지 않는다. 그래서 통제 지점을 **병합 승인**으로 옮긴다.

| | 푸시(제안) | **병합 승인(반영)** |
|---|---|---|
| 대상 | 작업 브랜치 | `main` |
| 누가 | **누구나** (문서를 고칠 수 있는 사람 전부) | **변경 내용에 따라 다름** |
| 의미 | "이렇게 바꾸면 어떨까요" | **"반영한다"** |

**푸시를 막지 않는 이유가 있다.**

- 부서 담당자가 "이 문서는 법정 항목 같은데요"라고 **초안을 올리는 것 자체가 유용하다.**
  제안조차 못 하게 하면 잘못된 문서가 그대로 방치된다
- 푸시를 막아도 안전해지지 않는다. 어차피 `main` 병합이 유일한 반영 경로다
- 브랜치 이름 규칙으로 막는 방식은 우회할 수 있지만, **승인 게이트는 우회할 수 없다**

즉 **제안은 열고, 반영은 잠근다.** `main` 브랜치는 보호 설정으로 **직접 푸시를 전면 금지**한다
— 이것이 유일하게 필요한 푸시 제한이다.

#### 4.7.1.1 승인 매트릭스

변경 내용에 따라 필요한 승인자가 달라진다. CI가 MR diff를 검사해 라벨을 붙이고, 라벨별 필수
승인자를 저장소 규칙으로 강제한다.

| 변경 유형 | CI 라벨 | 필수 승인자 |
|---|---|---|
| 본문·절 제목·FAQ 수정 | — | 소유 부서 리뷰어 1명 |
| `version` · `valid_until` 조정 | — | 소유 부서 리뷰어 1명 |
| 문서 신규 등록 | `문서신규` | 소유 부서 **팀장** + 인사팀 |
| 문서 폐기 (`status: expired`) | `문서폐기` | 소유 부서 **팀장** |
| **`owner_dept` 변경** | `소유권이전` | **넘기는 부서 팀장 + 받는 부서 팀장** |
| **`authority_level` 변경** | `위계변경` | **인사팀장** |
| **`acl_groups` · `sensitivity` 변경** | `권한변경` | **인사팀장 + 보안 담당자** |
| **`statutory` 변경** | `법정항목` | **인사팀 지정 담당자** (개인 지정, 법무 검토 권장) |

**`statutory`만 개인 지정인 이유.** 어떤 항목이 법정 최소 기준의 적용을 받는지는 **전사에서
하나로 판단해야 한다.** 부서마다 다르게 붙으면 같은 제도에 대해 어떤 문서는 고지가 나가고
어떤 문서는 안 나간다. 그리고 이 판단이 틀리면 **위법한 안내가 나간다** — 다른 필드와 위험의
성격이 다르다.

**`owner_dept` 변경에 양쪽 팀장이 필요한 이유.** 받는 부서가 모르는 채로 문서를 떠안으면,
그 문서는 주인이 없는 상태가 된다. 소유권 이전은 합의여야 한다.

```text
# CODEOWNERS — 경로 단위 (기본 리뷰어)
knowledge/HR-*     @hr-team
knowledge/DEV-*    @dev-team
knowledge/OPS-*    @ops-team
knowledge/REG-*    @hr-team

# 아래는 CODEOWNERS로 표현할 수 없다 — CI 라벨 + 병합 승인 규칙으로 강제한다
권한변경    → @hr-lead + @security
위계변경    → @hr-lead
소유권이전  → @<from>-lead + @<to>-lead
법정항목    → @hr-legal-owner   (개인)
```

#### 4.7.1.2 병목을 만들지 않는다

**오탈자 하나 고치는 데 팀장 승인을 받게 하면 아무도 문서를 고치지 않는다.** 그러면 문서가
낡고, 챗봇 답변이 틀리고, 시스템 전체가 무의미해진다. 그래서 등급을 나눈 것이다.

- 본문 수정은 **동료 리뷰 1명**으로 끝난다. 대부분의 변경이 여기 속한다
- 팀장·인사팀 승인은 **문서 하나를 넘어 영향이 가는 변경**에만 요구한다
- 승인 대기가 3영업일을 넘으면 자동으로 알림을 올린다

**긴급 되돌리기(break-glass).** 잘못된 권한 설정이 배포됐을 때 팀장 승인을 기다릴 수 없다.
**`revert` 커밋은 승인 1명으로 병합 가능**하게 하되, 병합 즉시 보안 담당자에게 통보하고
사후에 정식 검토를 받는다. 되돌리는 방향은 언제나 안전한 쪽이다.

> **담당자 실무 절차는 [`문서 관리자 가이드`](../docs/document-admin-guide.md)에 있다.**
> Git을 처음 쓰는 인사담당자를 위해 소스트리(GUI) 기준으로 단계별로 정리했다.

#### 4.7.2 파이프라인

```text
[담당자 푸시] → [MR] → [CI 검증] → [승인] → [main 병합] → [자동 배포]
                          │            │                       │
                    실패 시 차단   권한변경 라벨이면        색인 원자적 교체
                                   승인자 추가 필요         실패 시 기존 색인 유지
```

| 단계 | 실행 | 실패 시 |
|---|---|---|
| 1 | `tools/validate_docs.py` — front-matter·규정 필드·고지·중복 | **병합 차단** |
| 2 | `tools/run_eval.py` — 골든셋 회귀 | **병합 차단** |
| 3 | `tools/tune_thresholds.py` — 게이트 분리 구간 확인 | 경고 + 문서 보강 요구 |
| 4 | 권한·위계·소유권·법정항목 diff 검사 | 해당 라벨 부여 → **§4.7.1.1 승인자 추가** |
| 5 | 병합 후 색인 갱신 | 이전 색인 유지, 배포 실패 알림 |
| 6 | 배포 후 스모크 (문서 수·청크 수·표본 질의) | **자동 롤백** |

2단계가 핵심이다. 문서 하나를 고쳤는데 **다른 질문의 답이 틀어지는 일**이 실제로 발생하므로,
사람이 기억해서 돌리는 것이 아니라 병합 조건으로 강제한다.

**사내 GitLab 예시**

```yaml
stages: [validate, deploy]

문서검증:
  stage: validate
  image: registry.internal/onboarding-rag/ci:1.0   # 반입된 이미지 (§5)
  script:
    - python3 tools/validate_docs.py
    - python3 tools/run_eval.py
    - python3 tools/tune_thresholds.py || echo "분리 구간 경고"
  rules: [{ if: $CI_PIPELINE_SOURCE == "merge_request_event" }]

색인배포:
  stage: deploy
  script:
    - python3 -m app.indexing.build_index --atomic
    - python3 tools/smoke_check.py --endpoint http://api.internal:8000
  rules: [{ if: $CI_COMMIT_BRANCH == "main" }]
```

#### 4.7.3 폐쇄망 CI의 제약

일반적인 CI 설정을 그대로 쓸 수 없다. 다음이 다르다.

| 항목 | 폐쇄망에서 |
|---|---|
| CI 러너 이미지 | **반입 대상이다** (§5). 외부 레지스트리에서 pull하지 않는다 |
| 의존성 설치 | 파이프라인 중 외부 설치 금지. **러너 이미지에 미리 포함**하거나 내부 미러 사용 |
| 외부 액션·플러그인 | 사용하지 않는다. **저장소 안의 스크립트만** 실행한다 |
| 러너 egress | 차단. 내부 레지스트리·Git·배포 대상만 허용 |

> 이 프로토타입의 런타임 외부 의존성은 **numpy와 PyYAML 둘뿐**이다. 폐쇄망 러너 이미지를
> 만들기가 그만큼 쉽고, 반입 대장도 짧아진다. scikit-learn을 걷어낸 결정(§11 기술설계서
> 교훈 10)이 여기서 두 번째 값을 한다.

#### 4.7.4 배포 = 색인 갱신

문서 변경 배포는 **컨테이너 재배포가 아니라 색인 갱신**이다. 코드가 바뀌지 않기 때문이다.

- **소요:** 전체 재색인 실측 **286ms / 14종**. 선형 확장 시 1,000종에서도 수십 초 수준이다.
  증분 색인의 복잡도를 감수할 이유가 없다 — **매번 전체 재색인**이 단순하고 안전하다
- **원자적 교체:** 새 색인을 메모리에 완성한 뒤 참조만 바꾼다. 만드는 도중 실패하면
  **기존 색인이 그대로 서비스**한다. 반쯤 갱신된 상태가 존재하지 않는다
- **무중단:** 요청 처리 중인 스레드는 이전 색인을 계속 본다

#### 4.7.5 롤백

| 상황 | 대응 |
|---|---|
| 잘못된 내용이 배포됨 | `git revert` → 같은 파이프라인으로 **자동 재배포** |
| 색인 생성 실패 | 이전 색인 유지. 서비스는 계속 동작하고 배포만 실패 알림 |
| 스모크 실패 | 직전 커밋으로 자동 롤백 |
| **권한 필드 오설정** | 배포는 되지만 §4.6.4 최고 등급으로 **보안 담당자에게 즉시 통보**. 발견 즉시 revert |

마지막 줄이 중요하다. 권한 사고는 CI가 "틀렸다"고 판단할 수 없다 — 전사 공개가 의도된
변경일 수도 있기 때문이다. 그래서 **막는 것이 아니라 승인을 요구하고, 배포 후 즉시 알린다.**

## 5. 모델·이미지 반입 절차 (D3)

폐쇄망은 "인터넷이 없다"가 아니라 "무엇이 들어왔는지 추적된다"는 뜻이다.

1. **선정** — 모델 라이선스와 상용 이용 가능 여부를 확인하고 기록한다.
2. **수집** — 인터넷 구간의 별도 준비 서버에서 모델 파일과 베이스 이미지를 받는다.
3. **검증** — 공개된 해시와 대조하고, 결과를 반입 대장에 기록한다.
4. **점검** — 이미지 취약점 스캔과 악성코드 검사를 수행한다.
5. **승인** — 보안 담당자가 반입을 승인한다.
6. **반입** — 내부 레지스트리 또는 아티팩트 저장소에 등록한다.
7. **대장 기록** — 모델명·버전·해시·반입일·승인자·용도를 남긴다.

운영 중 컨테이너는 외부에서 무언가를 받지 않는다. 모든 갱신은 이 절차를 다시 거친다.

## 6. 로그와 보존 기간 (D6)

### 6.1 보존 기간

| 로그 유형 | 보존 | 내용 | 접근 권한 |
|---|---|---|---|
| 질의 품질 로그 | **90일** | 질문 해시, 카테고리, 게이트 결과, 인용 문서ID·버전 | 서비스 운영자 |
| **문서 권한 변경 이력** | **3년** | `acl_groups`·`sensitivity`·`authority_level`·`statutory`의 **변경 전후 값**, 변경자, 승인자 (§4.6.4 최고 등급) | 보안 담당자 |
| 감사 로그 | **1년** | 권한 거부, 관리자 조회, 문서 발행·폐기 이력, 본문 변경 diff | 보안 담당자 |
| 문서 열람 로그 | **90일** | 문서 목록 조회, 관리자의 개별 문서 열람 (§4.6.5) | 보안 담당자 |
| 보안 이벤트 | **1년** | 인젝션 시도, 민감정보 차단 (유형만) | 보안 담당자 |
| 접근 로그 (프록시) | **90일** | 시각, 사용자 식별자, 엔드포인트, 상태 코드 | 인프라 운영자 |
| 오류·성능 로그 | **30일** | 스택 트레이스, 응답 시간 | 서비스 운영자 |
| 세션 | **30분** | 메모리 전용, 영속화하지 않음 | 없음 |
| 사용자 저장 항목 | **재직 중 유지** | 북마크·저장한 답변·체크리스트 | **본인만** |

### 6.2 남기지 않는 것

- 질문 원문 (해시와 카테고리만 남긴다)
- 주민등록번호·계좌번호·카드번호·비밀번호·인증번호
- 건강검진 결과 등 건강정보
- 차단된 입력의 원문 (탐지 유형과 시각만 남긴다)

### 6.3 파기

보존 기간이 지난 로그는 자동 파기하고 파기 이력을 남긴다. 퇴사자의 저장 항목은 계정 정리 절차에
따라 삭제한다. 사용자는 언제든 본인의 저장 항목을 직접 삭제할 수 있다.

## 7. 네트워크·접근 통제 체크리스트

- [ ] 챗봇·LLM·임베딩·벡터 DB를 사내망 또는 승인된 폐쇄망에 둔다.
- [ ] 모델 추론 컨테이너와 벡터 DB의 인터넷 egress를 기본 차단한다.
- [ ] 일반 사용자는 UI/API만 접근하고 DB·모델 서버·관리 콘솔에 직접 접근하지 못한다.
- [ ] 서비스 간 통신은 필요한 포트만 열고 인증·암호화를 적용한다.
- [ ] 사내 SSO로 사용자 역할을 **서버에서** 검증한다. 클라이언트가 보낸 식별자를 신뢰하지 않는다.
- [ ] 문서 ACL을 검색 전 필터와 결과 반환 전 재검증 **양쪽에** 적용한다.
- [ ] API 키·DB 비밀번호·서비스 계정은 서버 환경변수 또는 비밀관리 도구에만 둔다.
- [ ] 모델·이미지·의존성 반입 이력과 취약점 점검 결과를 관리한다.
- [ ] 의존성 버전을 정확히 고정한다(`==`). 범위 지정을 쓰지 않는다.
- [ ] 백업도 암호화하고 복구 절차와 접근 권한을 검토한다.
- [ ] 보안 헤더(CSP·nosniff·Referrer-Policy·Permissions-Policy)를 응답에 적용한다.

## 8. Fail-safe 기준

| 상황 | 챗봇 동작 | 운영 조치 |
|---|---|---|
| 권한 밖 문서 요청 | 근거 부족과 **동일한 문구**로 응답 (존재 노출 금지) | 감사 로그 기록 |
| 근거 부족·문서 충돌 | 추정 없이 담당 부서 안내 | 문서 보강 대상으로 기록 |
| 민감정보 입력 | 입력 거부, 원문 미저장 | 유형만 보안 이벤트로 기록 |
| 문서 만료 | 최신본 확인 안내, 만료 문서 인용 금지 | 문서 소유자에게 갱신 알림 |
| 모델·DB 장애 | 추정 금지, 장애 안내와 담당자 연결 | 운영자 원인 분석·복구 |
| 정책 오류 의심 | 해당 문서/버전 즉시 비활성화 | 인사·보안 검토 후 재발행 |

## 9. 단계별 구축 절차 (D7)

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 네트워크 구간 설계·방화벽 정책 수립 | 구간 간 통신 매트릭스 승인 |
| 2 | 모델·이미지 반입 (§5) | 반입 대장 기록 완료 |
| 3 | 데이터 계층 기동 (벡터 DB, RDB) | 헬스체크 통과, 백업 설정 완료 |
| 4 | 모델 계층 기동 (임베딩, LLM) | egress 차단 확인, 추론 응답 확인 |
| 5 | **문서 정비 (§4.5)** — 변환·구조 정비·메타데이터 부여 | 정비 체크리스트(§4.5.7) 통과. 정리 서버 egress 차단 확인 |
| 5-1 | 문서 수집·승인·색인 파이프라인 구축 | 승인 없는 문서가 색인되지 않음을 검증 |
| 5-2 | **CI/CD 구성 (§4.7)** — 러너 반입, 검증 파이프라인, 자동 배포 | 검증 실패 MR이 병합되지 않음을 확인. `main` 직접 푸시 차단 확인. §4.7.1.1 승인 매트릭스가 라벨별로 동작함을 확인 |
| 6 | 앱 배포 및 SSO 연동 | 서버측 권한 재검증 동작 확인 |
| 7 | 권한·가드레일 검증 | 권한 밖 문서 차단률 100% 확인 |
| 8 | 골든셋 평가 실행 | Recall·인용 충실도·차단률 기준 충족 |
| 9 | 모니터링·백업·로그 보존 설정 | 보존 기간 자동 적용 확인 |
| 10 | 파일럿 운영 | 대상 부서 시범 사용 후 지표 검토 |

**5단계가 일정의 대부분을 차지한다.** 메타데이터 부여는 자동화되지 않으며, 이 서비스의 권한
보장이 그 위에서만 성립한다(§4.5.1).

**7단계와 8단계는 생략할 수 없다.** 권한 통제와 안전 응답이 이 서비스의 존재 이유이므로,
동작 확인 없이 다음 단계로 넘어가지 않는다.

## 10. 백업·복구

| 대상 | 방식 | 목표 |
|---|---|---|
| 문서 원본·메타데이터 | 일 1회 전체 + 변경분 | RPO 24시간 / RTO 4시간 |
| 사용자 저장 항목 | 일 1회 | RPO 24시간 / RTO 4시간 |
| 벡터 인덱스 | **백업하지 않는다** | 원본에서 재생성 (실측 286ms / 14종 기준) |
| 감사 로그 | 일 1회, 변조 방지 저장소 | RPO 24시간 |
| 모델 파일 | 반입 대장 기준 재반입 | RTO 8시간 |

벡터 인덱스를 백업 대상에서 뺀 것은 **원본에서 결정적으로 재생성되기 때문**이다. 백업 대상을
줄이면 복구 절차도 단순해진다.

| 구분 | 수집 지표 |
|---|---|
| 서비스 | 요청 수, 오류율, 응답 지연 P50/P95, 세션 수 |

## 12. 법·규정 고려사항 (D9)

> ⚠️ 아래는 설계 시 검토가 필요한 항목을 정리한 것이며 법률 자문이 아니다. 조문은 개정될 수 있으므로
> **원문 확인과 법무·인사 담당자 검토를 거쳐 확정한다.**

| 영역 | 검토 항목 | 설계 반영 |
|---|---|---|
| 개인정보보호법 | 최소수집·목적제한, 처리 위탁, 국외 이전 | 개인정보를 벡터 DB에 넣지 않는다. 외부 API로 질문·문서를 전송하지 않으므로 국외 이전 쟁점이 발생하지 않는다 — **온프레미스를 선택하는 핵심 근거다** |
| 개인정보보호법 | 보존 기간과 파기 | §6 보존 기간표, 자동 파기 |
| 개인정보보호법 | 접근 통제·접속 기록 | 서버측 RBAC, 감사 로그 1년 |
| 산업안전보건법 | 일반건강진단 주기 | 사무직 2년 1회로 알려져 있다. 프로토타입의 "2년 1회" 가정은 이 주기와 부합하나, **실제 적용 전 조문과 담당자 확인이 필요하다** |
| 소득세법 | 연말정산 증빙, 이직자 원천징수영수증 | 챗봇은 안내만 하고 세무 판단을 하지 않는다 |
| 근로기준법 | 인사 서류 보존 | 문서 저장소 보존 정책과 정합 확인 |

**온프레미스 선택의 근거를 한 줄로:** 외부로 나가지 않으면 국외 이전·처리 위탁 쟁점이
발생하지 않고, 접속 기록과 접근 통제를 조직이 직접 통제할 수 있다.

## 13. 비용 비교 (D8)

> 아래는 구조를 보여주기 위한 산정 틀이며, 실제 단가는 조달 조건에 따라 다르다.

| 구분 | 온프레미스 | 외부 LLM API |
|---|---|---|
| 초기 비용 | GPU 서버·스토리지 도입, 구축 공수 | 거의 없음 |
| 변동 비용 | 전력·상면·운영 인건비 (사용량과 무관하게 고정) | 토큰 사용량에 비례 |
| 규모 효과 | 질의가 늘어도 비용이 크게 늘지 않는다 | 질의에 비례해 선형 증가 |
| 데이터 통제 | 조직이 전부 통제 | 위탁·국외 이전 검토 필요 |
| 손익 분기 | 질의량이 일정 수준을 넘으면 유리 | 초기·소규모에 유리 |

**판단 기준:** 500명 조직에서 일 225회 질의는 API 비용만 보면 온프레미스가 불리할 수 있다.
그럼에도 온프레미스를 선택하는 이유는 비용이 아니라 **데이터 통제**다. 비용 비교는 그 선택의
크기를 파악하기 위한 것이지, 선택의 근거가 아니다.

## 15. 남은 확정 사항

- 실제 SSO/IdP 제품과 그룹 매핑 방식 (사내 설치형 IdP 전제. 외부 IdP는 범위 밖)
- 문서 정비 대상 선정 — 온보딩 질문 30~50개 수집 후 확정 (§4.5.6)
- 승인 매트릭스(§4.7.1.1)의 실제 그룹·개인 매핑 — 특히 `statutory` 지정 담당자
- `authority_level` 판정 주체와 법무 검토 범위
- 벡터 DB 제품 선정 (ACL 필터 성능 검증 포함)
- LLM 모델 선정과 라이선스 검토
- 실제 문서 분류 체계·문서별 ACL·민감도 등급
- 보안관제(SIEM) 연동 범위
- 법·규정 항목의 조문 확인과 담당자 검토
