# On-premise RAG 챗봇 구축 설계

| 항목 | 내용 |
|---|---|
| 문서 ID | DOC-003 |
| 버전 | v2.0 |
| 개정일 | 2026-08-31 |
| 목적 | 온보딩 RAG 챗봇을 사내 폐쇄 환경에 구축하는 방안을 설계한다 |
| 관련 문서 | [`../prototype/docs/technical-design.md`](../prototype/docs/technical-design.md) · [`../docs/user-guide.md`](../docs/user-guide.md) · [`../docs/plan.md`](../docs/plan.md) |

> **이 문서의 위치:** 프로토타입은 **동작으로** 증명하고, On-premise 구축은 **설계로** 증명한다.
> 프로토타입은 온프레미스 환경에서 실행되지 않는다. 이 문서는 그 전환을 어떻게 하는지를 다룬다.
>
> **핵심 원칙:** 사내 문서 원문, 사용자 질문, 임베딩, 추론 결과가 외부 LLM API나 외부 벡터 DB로
> 전송되지 않도록 구성한다.

---

## 0. 프로토타입과 목표 운영 환경

| | 프로토타입 (구현 완료) | 목표 운영 환경 (이 문서) |
|---|---|---|
| 증명 방식 | 실행되는 시연 | 설계 문서 |
| 배포 위치 | 로컬 / 일반 호스팅 | 사내망 또는 통제된 폐쇄망 |
| 지식 데이터 | 합성 온보딩 문서 9종 | 승인된 실제 사내 문서 |
| 인증 | 사번 선택 화면 | 사내 SSO + 서버측 RBAC |
| 답변 생성 | 추출 기반 (근거 정리형) | 사내 LLM 추론 서버 |
| 임베딩 | 코퍼스 학습형 TF-IDF | 사내 임베딩 서버 |
| 외부 API 호출 | 없음 | 없음 |

### 전환 경계는 코드에 실재한다

설계 문서의 주장이 공허하지 않으려면 전환 지점이 코드에 있어야 한다. 프로토타입은 세 개의
인터페이스로 이 경계를 구현했다.

| 계층 | 전환 시 교체 대상 | 코드 위치 |
|---|---|---|
| 임베딩 | `EmbeddingBackend` 구현체 | `app/retrieval/embedder.py` |
| 답변 생성 | `AnswerBackend` (extractive → llm) | `app/answer/` |
| 인증 | 데모 로그인 → SSO | `app/main.py`, `app/session.py` |

검색·권한 판정·가드레일·답변 구조화는 **전환해도 바뀌지 않는다.**

## 1. 아키텍처

### 1.1 논리 구성

```text
[사내 사용자 브라우저]
   │  사내망 HTTPS
   ▼
[리버스 프록시 / TLS 종단]          ← 보안 헤더, 요청 제한, 접근 로그
   │
   ▼
[챗봇 UI + API (RAG 오케스트레이터)]
   ├─ 입력 검증 · 민감정보 검사 · 정책 검사
   ├─ 권한 필터 기반 검색 ─────────► [벡터 DB]  (ACL 메타데이터 포함)
   │                          └──► [BM25 색인]
   ├─ 근거 충분성 판정
   ├─ 임베딩 요청 ─────────────────► [사내 임베딩 서버]
   ├─ 답변 생성 요청 ───────────────► [사내 LLM 추론 서버]
   └─ 답변 검증 (인용 · 권한 재검증 · 민감정보)
   │
   ▼
[권한 정책 서비스] ◄── [사내 SSO / IdP]     [문서 저장소]
                                            └─ [문서 수집·승인·색인 파이프라인]
[감사 로그 · 모니터링]  ← 최소 수집 · 접근 통제 · 보존 정책
```

### 1.2 네트워크 구간 분리

| 구간 | 배치 | 인바운드 | 아웃바운드 |
|---|---|---|---|
| DMZ-사내 | 리버스 프록시 | 사내 사용자 443 | 앱 구간만 |
| 앱 | 챗봇 UI/API | 프록시에서만 | 데이터·모델 구간 |
| 모델 | LLM · 임베딩 서버 | 앱 구간에서만 | **인터넷 egress 차단** |
| 데이터 | 벡터 DB · 문서 저장소 · RDB | 앱 구간에서만 | **인터넷 egress 차단** |
| 관리 | 색인 파이프라인 · 운영 콘솔 | 관리자 네트워크에서만 | 내부 레지스트리만 |

일반 사용자 네트워크에서 모델·데이터·관리 구간에 직접 접근할 수 없다.

## 2. 구성 요소와 자원 산정 (D1)

### 2.1 프로토타입 실측값

아래는 프로토타입을 실제로 측정한 값이다. 추정이 아니라 측정 결과이며, 운영 규모 산정의 기준선이다.

| 항목 | 측정값 | 조건 |
|---|---|---|
| 지식 문서 | 26.0 KB / 9종 | 마크다운 원본 |
| 청크 수 | 43개 | 목표 400자 · 최대 700자 |
| 벡터 저장 | 88.9 KB | TF-IDF 희소 표현 |
| 부팅 시간 (색인 포함) | 146 ms | 전체 재색인 포함 |
| 상주 메모리 | 34 MB | Python + numpy (외부 ML 라이브러리 없음) |
| 응답 지연 P50 | 1.6 ms | 추출 기반, LLM 미사용 |
| 응답 지연 P95 | 2.9 ms | n=84 |

**해석:** 검색·권한 판정·답변 구조화는 **비용이 거의 없다.** 운영 환경의 자원 산정은 사실상
**LLM 추론과 임베딩 모델이 전부 결정한다.**

### 2.2 운영 환경 자원 산정

문서 규모를 실측값에서 선형 확장해 추정한다.

| 지식 규모 | 예상 청크 | 임베딩 저장 (1024dim, float32) | 벡터 DB 메모리 |
|---|---|---|---|
| 문서 100종 (약 300KB) | 약 500 | 약 2 MB | 수십 MB |
| 문서 1,000종 (약 3MB) | 약 5,000 | 약 20 MB | 수백 MB |
| 문서 10,000종 (약 30MB) | 약 50,000 | 약 200 MB | 1~2 GB |

→ **벡터 저장은 병목이 아니다.** 1만 종 규모에서도 일반적인 서버 메모리로 충분하다.

**LLM 추론 서버 (모델 크기별)**

| 모델 규모 | 정밀도 | 가중치 VRAM | KV 캐시 여유 | 권장 GPU |
|---|---|---|---|---|
| 7~8B | INT4 양자화 | 약 5 GB | +3 GB | 16GB 1장 |
| 7~8B | FP16 | 약 16 GB | +6 GB | 24GB 1장 |
| 14B | INT4 | 약 9 GB | +5 GB | 24GB 1장 |
| 32B | INT4 | 약 20 GB | +8 GB | 48GB 1장 또는 24GB 2장 |

**임베딩 서버:** 소형 다국어 모델(100~300M)은 CPU로도 동작하며 GPU 사용 시 1~2 GB VRAM이면 충분하다.

**동시 사용자 대비 산정 (500명 조직 가정)**

| 항목 | 가정 | 산정 |
|---|---|---|
| 전체 직원 | 500명 | — |
| 일 활성 사용자 | 15% | 75명 |
| 1인당 일 질의 | 3회 | 225회/일 |
| 피크 집중 | 업무시간 8h 중 2h에 50% | 약 1.0 QPS |
| LLM 응답 시간 | 스트리밍 첫 토큰 1초, 완료 5초 | — |
| 필요 동시 처리 | 1.0 QPS × 5초 | 약 5 동시 요청 |

→ **7~8B INT4 모델 + 24GB GPU 1장으로 500명 조직을 감당할 수 있다.** GPU 이중화는 가용성을 위한
것이지 처리량 때문이 아니다.

### 2.3 서버 구성 권장안

| 역할 | CPU | RAM | 디스크 | GPU |
|---|---|---|---|---|
| 앱 (UI/API/오케스트레이터) | 4 vCPU | 8 GB | 50 GB | — |
| 임베딩 서버 | 4 vCPU | 8 GB | 30 GB | 선택 (없어도 동작) |
| LLM 추론 서버 | 8 vCPU | 32 GB | 200 GB (모델 파일) | 24GB 1장 |
| 벡터 DB + RDB | 4 vCPU | 16 GB | 200 GB (SSD) | — |
| 색인 파이프라인 | 4 vCPU | 8 GB | 100 GB | — |

> 앱 계층의 실측 상주 메모리는 **34MB**다. 위 사양은 동시 요청과 운영 여유를 감안한 값이며,
> 실제 병목은 앱이 아니라 LLM 추론이다.

소규모 도입은 앱·임베딩·벡터 DB를 한 서버에 합치고 LLM 서버만 분리해도 된다.

## 3. 컨테이너 구성 (D2)

### 3.1 구성표

| 서비스 | 이미지 | 포트 | 볼륨 | 네트워크 | egress |
|---|---|---|---|---|---|
| `proxy` | nginx (내부 미러) | 443 | TLS 인증서 (읽기 전용) | dmz, app | 없음 |
| `api` | 자체 빌드 (Python 3.11) | 8000 | 설정 (읽기 전용) | app, data, model | 없음 |
| `embedder` | 자체 빌드 + 모델 파일 | 8001 | 모델 (읽기 전용) | model | **차단** |
| `llm` | vLLM 또는 동등 | 8002 | 모델 (읽기 전용) | model | **차단** |
| `vectordb` | 벡터 DB | 6333 | 데이터 (영속) | data | **차단** |
| `db` | PostgreSQL | 5432 | 데이터 (영속) | data | **차단** |
| `indexer` | 자체 빌드 | — | 문서 저장소, 데이터 | data, model, admin | 내부 레지스트리만 |

### 3.2 배치 원칙

- 모든 이미지는 **내부 레지스트리에서만** 가져온다. 실행 시점의 외부 pull을 금지한다.
- `embedder`·`llm`·`vectordb`·`db`는 인터넷 egress를 기본 차단한다. 모델 파일은 이미지 또는
  마운트 볼륨으로 미리 넣는다.
- 컨테이너는 비-root 사용자로 실행하고 루트 파일시스템을 읽기 전용으로 둔다. 쓰기가 필요한
  경로만 볼륨으로 연다.
- 비밀값은 이미지에 넣지 않고 오케스트레이터의 시크릿으로 주입한다.
- 서비스 간 통신은 필요한 포트만 열고 mTLS 또는 내부 인증을 적용한다.

### 3.3 헬스체크와 기동 순서

```text
db, vectordb  →  embedder, llm  →  indexer(최초 색인)  →  api  →  proxy
```

`api`는 `embedder`·`llm`·`vectordb`가 준비되기 전에는 준비 상태를 보고하지 않는다.
기동 실패 시 추정 답변을 내지 않고 장애 안내로 전환한다.

## 4. 데이터 흐름과 보안 경계

### 4.1 문서 등록

```text
[인사담당자 초안] → [카테고리·대상·ACL·민감도·유효기간 입력] → [검토·승인]
  → [문서 파싱 · 악성 파일 검사] → [청크화 · 임베딩] → [벡터 DB 색인] → [검색 가능]
```

- 승인 전 문서는 검색 결과에 절대 포함되지 않는다. 프로토타입은 이를 `status != published`이면
  색인하지 않는 것으로 구현했고, 필수 필드 누락은 경고가 아니라 **색인 실패**로 처리한다.
- 변경·폐기 시 이전 버전과 변경 사유를 보존하고, 폐기 문서는 즉시 검색에서 제외한다.
- 개인 프로필, 계좌·신분증·건강정보, 개인별 신청 상태는 청크나 벡터 DB에 넣지 않는다.

### 4.2 질문·답변

```text
[질문] → [인증·역할 확인] → [입력 검증] → [민감정보 검사]
  → [★1차 권한 필터] → [하이브리드 검색] → [근거 충분성 판정]
  → [답변 생성] → [★2차 권한 재검증] → [출력 검사] → [답변 + 근거 + 다음 행동]
```

권한은 **검색 전과 답변 반환 전 두 번** 확인한다. 프로토타입에 두 지점 모두 구현되어 있다.

### 4.3 개인화 경계

공통 온보딩 문서만 RAG 지식베이스로 관리하고, 개인화는 별도 정책 서비스에서 최소 속성만 조회해
분기한다. **이 문서가 개인화 원칙의 단일 출처다.**

| 허용 속성 | 용도 |
|---|---|
| 사번 | 식별용. 화면에는 `12****`로 마스킹 |
| 입사일 | 건강검진·입사 절차 대상 여부 계산 |
| 신규/계속/이직 구분 | 안내 문서·체크 항목 분기 |
| 소속·역할 | 접근 가능 문서 필터 |

- 개인 원본값은 벡터 DB에 넣지 않고 LLM 프롬프트에도 불필요하게 전달하지 않는다.
- 챗봇에는 "현재 대상입니다/아닙니다" 같은 **파생된 결과만** 제공한다.
- 어떤 조건으로 판정했는지 사용자에게 한 줄로 밝힌다.
- HR·관리자는 업무상 필요한 최소 범위만 열람하고 조회 목적·대상·시각을 감사한다.
- **사용자가 직접 저장한 항목**(북마크·저장한 답변·체크리스트)은 본인만 조회하며, HR·관리자도
  열람할 수 없다. 저장 전 민감정보 검사를 통과한 것만 저장한다.

## 5. 모델·이미지 반입 절차 (D3)

폐쇄망은 "인터넷이 없다"가 아니라 "무엇이 들어왔는지 추적된다"는 뜻이다.

1. **선정** — 모델 라이선스와 상용 이용 가능 여부를 확인하고 기록한다.
2. **수집** — 인터넷 구간의 별도 준비 서버에서 모델 파일과 베이스 이미지를 받는다.
3. **검증** — 공개된 해시와 대조하고, 결과를 반입 대장에 기록한다.
4. **점검** — 이미지 취약점 스캔과 악성코드 검사를 수행한다.
5. **승인** — 보안 담당자가 반입을 승인한다.
6. **반입** — 내부 레지스트리 또는 아티팩트 저장소에 등록한다.
7. **대장 기록** — 모델명·버전·해시·반입일·승인자·용도를 남긴다.

운영 중 컨테이너는 외부에서 무언가를 받지 않는다. 모든 갱신은 이 절차를 다시 거친다.

## 6. 로그와 보존 기간 (D6)

### 6.1 보존 기간

| 로그 유형 | 보존 | 내용 | 접근 권한 |
|---|---|---|---|
| 질의 품질 로그 | **90일** | 질문 해시, 카테고리, 게이트 결과, 인용 문서ID·버전 | 서비스 운영자 |
| 감사 로그 | **1년** | 권한 거부, 관리자 조회, 문서 발행 이력 | 보안 담당자 |
| 보안 이벤트 | **1년** | 인젝션 시도, 민감정보 차단 (유형만) | 보안 담당자 |
| 접근 로그 (프록시) | **90일** | 시각, 사용자 식별자, 엔드포인트, 상태 코드 | 인프라 운영자 |
| 오류·성능 로그 | **30일** | 스택 트레이스, 응답 시간 | 서비스 운영자 |
| 세션 | **30분** | 메모리 전용, 영속화하지 않음 | 없음 |
| 사용자 저장 항목 | **재직 중 유지** | 북마크·저장한 답변·체크리스트 | **본인만** |

### 6.2 남기지 않는 것

- 질문 원문 (해시와 카테고리만 남긴다)
- 주민등록번호·계좌번호·카드번호·비밀번호·인증번호
- 건강검진 결과 등 건강정보
- 차단된 입력의 원문 (탐지 유형과 시각만 남긴다)

### 6.3 파기

보존 기간이 지난 로그는 자동 파기하고 파기 이력을 남긴다. 퇴사자의 저장 항목은 계정 정리 절차에
따라 삭제한다. 사용자는 언제든 본인의 저장 항목을 직접 삭제할 수 있다.

## 7. 네트워크·접근 통제 체크리스트

- [ ] 챗봇·LLM·임베딩·벡터 DB를 사내망 또는 승인된 폐쇄망에 둔다.
- [ ] 모델 추론 컨테이너와 벡터 DB의 인터넷 egress를 기본 차단한다.
- [ ] 일반 사용자는 UI/API만 접근하고 DB·모델 서버·관리 콘솔에 직접 접근하지 못한다.
- [ ] 서비스 간 통신은 필요한 포트만 열고 인증·암호화를 적용한다.
- [ ] 사내 SSO로 사용자 역할을 **서버에서** 검증한다. 클라이언트가 보낸 식별자를 신뢰하지 않는다.
- [ ] 문서 ACL을 검색 전 필터와 결과 반환 전 재검증 **양쪽에** 적용한다.
- [ ] API 키·DB 비밀번호·서비스 계정은 서버 환경변수 또는 비밀관리 도구에만 둔다.
- [ ] 모델·이미지·의존성 반입 이력과 취약점 점검 결과를 관리한다.
- [ ] 의존성 버전을 정확히 고정한다(`==`). 범위 지정을 쓰지 않는다.
- [ ] 백업도 암호화하고 복구 절차와 접근 권한을 검토한다.
- [ ] 보안 헤더(CSP·nosniff·Referrer-Policy·Permissions-Policy)를 응답에 적용한다.

## 8. Fail-safe 기준

| 상황 | 챗봇 동작 | 운영 조치 |
|---|---|---|
| 권한 밖 문서 요청 | 근거 부족과 **동일한 문구**로 응답 (존재 노출 금지) | 감사 로그 기록 |
| 근거 부족·문서 충돌 | 추정 없이 담당 부서 안내 | 문서 보강 대상으로 기록 |
| 민감정보 입력 | 입력 거부, 원문 미저장 | 유형만 보안 이벤트로 기록 |
| 문서 만료 | 최신본 확인 안내, 만료 문서 인용 금지 | 문서 소유자에게 갱신 알림 |
| 모델·DB 장애 | 추정 금지, 장애 안내와 담당자 연결 | 운영자 원인 분석·복구 |
| 정책 오류 의심 | 해당 문서/버전 즉시 비활성화 | 인사·보안 검토 후 재발행 |

## 9. 단계별 구축 절차 (D7)

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 네트워크 구간 설계·방화벽 정책 수립 | 구간 간 통신 매트릭스 승인 |
| 2 | 모델·이미지 반입 (§5) | 반입 대장 기록 완료 |
| 3 | 데이터 계층 기동 (벡터 DB, RDB) | 헬스체크 통과, 백업 설정 완료 |
| 4 | 모델 계층 기동 (임베딩, LLM) | egress 차단 확인, 추론 응답 확인 |
| 5 | 문서 수집·승인·색인 파이프라인 구축 | 승인 없는 문서가 색인되지 않음을 검증 |
| 6 | 앱 배포 및 SSO 연동 | 서버측 권한 재검증 동작 확인 |
| 7 | 권한·가드레일 검증 | 권한 밖 문서 차단률 100% 확인 |
| 8 | 골든셋 평가 실행 | Recall·인용 충실도·차단률 기준 충족 |
| 9 | 모니터링·백업·로그 보존 설정 | 보존 기간 자동 적용 확인 |
| 10 | 파일럿 운영 | 대상 부서 시범 사용 후 지표 검토 |

**7단계와 8단계는 생략할 수 없다.** 권한 통제와 안전 응답이 이 서비스의 존재 이유이므로,
동작 확인 없이 다음 단계로 넘어가지 않는다.

## 10. 백업·복구

| 대상 | 방식 | 목표 |
|---|---|---|
| 문서 원본·메타데이터 | 일 1회 전체 + 변경분 | RPO 24시간 / RTO 4시간 |
| 사용자 저장 항목 | 일 1회 | RPO 24시간 / RTO 4시간 |
| 벡터 인덱스 | **백업하지 않는다** | 원본에서 재생성 (실측 146ms / 9종 기준) |
| 감사 로그 | 일 1회, 변조 방지 저장소 | RPO 24시간 |
| 모델 파일 | 반입 대장 기준 재반입 | RTO 8시간 |

벡터 인덱스를 백업 대상에서 뺀 것은 **원본에서 결정적으로 재생성되기 때문**이다. 백업 대상을
줄이면 복구 절차도 단순해진다.

## 11. 모니터링 (D4)

| 구분 | 수집 지표 |
|---|---|
| 서비스 | 요청 수, 오류율, 응답 지연 P50/P95, 세션 수 |
| 검색 품질 | 게이트 통과율, 근거 부족 비율, 인용 문서 분포 |
| 보안 | 권한 거부 건수, 민감정보 차단 건수, 인젝션 탐지 건수 |
| 모델 | 추론 지연, 큐 대기, GPU 사용률·메모리 |
| 문서 | 만료 임박 문서 수, 미승인 대기 문서 수 |

**알림 기준 예시** — 근거 부족 비율이 기준선의 2배를 넘으면 문서 보강이 필요하다는 신호이고,
권한 거부가 급증하면 ACL 설정 오류를 의심한다.

## 12. 법·규정 고려사항 (D9)

> ⚠️ 아래는 설계 시 검토가 필요한 항목을 정리한 것이며 법률 자문이 아니다. 조문은 개정될 수 있으므로
> **원문 확인과 법무·인사 담당자 검토를 거쳐 확정한다.**

| 영역 | 검토 항목 | 설계 반영 |
|---|---|---|
| 개인정보보호법 | 최소수집·목적제한, 처리 위탁, 국외 이전 | 개인정보를 벡터 DB에 넣지 않는다. 외부 API로 질문·문서를 전송하지 않으므로 국외 이전 쟁점이 발생하지 않는다 — **온프레미스를 선택하는 핵심 근거다** |
| 개인정보보호법 | 보존 기간과 파기 | §6 보존 기간표, 자동 파기 |
| 개인정보보호법 | 접근 통제·접속 기록 | 서버측 RBAC, 감사 로그 1년 |
| 산업안전보건법 | 일반건강진단 주기 | 사무직 2년 1회로 알려져 있다. 프로토타입의 "2년 1회" 가정은 이 주기와 부합하나, **실제 적용 전 조문과 담당자 확인이 필요하다** |
| 소득세법 | 연말정산 증빙, 이직자 원천징수영수증 | 챗봇은 안내만 하고 세무 판단을 하지 않는다 |
| 근로기준법 | 인사 서류 보존 | 문서 저장소 보존 정책과 정합 확인 |

**온프레미스 선택의 근거를 한 줄로:** 외부로 나가지 않으면 국외 이전·처리 위탁 쟁점이
발생하지 않고, 접속 기록과 접근 통제를 조직이 직접 통제할 수 있다.

## 13. 비용 비교 (D8)

> 아래는 구조를 보여주기 위한 산정 틀이며, 실제 단가는 조달 조건에 따라 다르다.

| 구분 | 온프레미스 | 외부 LLM API |
|---|---|---|
| 초기 비용 | GPU 서버·스토리지 도입, 구축 공수 | 거의 없음 |
| 변동 비용 | 전력·상면·운영 인건비 (사용량과 무관하게 고정) | 토큰 사용량에 비례 |
| 규모 효과 | 질의가 늘어도 비용이 크게 늘지 않는다 | 질의에 비례해 선형 증가 |
| 데이터 통제 | 조직이 전부 통제 | 위탁·국외 이전 검토 필요 |
| 손익 분기 | 질의량이 일정 수준을 넘으면 유리 | 초기·소규모에 유리 |

**판단 기준:** 500명 조직에서 일 225회 질의는 API 비용만 보면 온프레미스가 불리할 수 있다.
그럼에도 온프레미스를 선택하는 이유는 비용이 아니라 **데이터 통제**다. 비용 비교는 그 선택의
크기를 파악하기 위한 것이지, 선택의 근거가 아니다.

## 14. 해커톤 범위와 운영 전환의 구분

| 항목 | 프로토타입 (구현 완료) | 운영 전환 시 |
|---|---|---|
| 데이터 | 합성 문서 9종, 가상 프로필 4명 | 승인된 실제 문서, 최소 개인화 속성 |

| 검증 | 골든셋 28문항 자동 실행 | 지속적 품질·보안·운영 KPI 측정 |

## 15. 남은 확정 사항

- 실제 SSO/IdP 제품과 그룹 매핑 방식
- 벡터 DB 제품 선정 (ACL 필터 성능 검증 포함)
- LLM 모델 선정과 라이선스 검토
- 실제 문서 분류 체계·문서별 ACL·민감도 등급
- 보안관제(SIEM) 연동 범위
- 법·규정 항목의 조문 확인과 담당자 검토
